## Issues Identified

### Issue 1 — AC-09 Specification Gap: `<footer>` Element Not in Component

**Description:** AC-09 specifies that "the outermost element of the Site Footer rendering
is a `<footer>` landmark element." The `SiteFooter` component renders a `<div>` as its
outermost element. The `<footer>` landmark is instead provided by `Layout.tsx`, which
wraps the `headless-footer` AppPlaceholder in a `<footer>` element.

This is an intentional, documented architectural decision (implementation plan §Technical
Approach, run report §Assumptions). The final rendered HTML at the page level does include
a `<footer>` landmark, satisfying the accessibility requirement. The pattern is consistent
with how the Header component is structured (`<header>` from Layout.tsx, `<div>` from
the component).

The issue is a gap between the wording of AC-09 (which specifies the rendering's outermost
element) and the actual implementation (which delegates the landmark to Layout.tsx). The
functional and accessibility intent of the criterion is met; the literal component-level
wording is not.

**Severity:** Medium  
**Blocks Approval:** No  
**Recommended Action:** The human reviewer should acknowledge that AC-09 is satisfied at
the page level (via Layout.tsx) and that the architectural approach is consistent with the
established Header pattern. No code change is needed unless the reviewer decides the spec
wording should be enforced at the component level.

---

### Issue 2 — AC-12 Scenario 6: Missing `<footer>` Element Test

**Description:** AC-12 scenario 6 requires that "the rendered output contains a `<footer>`
element and a `<nav>` element." Test 11 verifies the `<nav>` element. No test verifies the
`<footer>` element at the component level, because `SiteFooter` does not render one (see
Issue 1). The test suite cannot assert what the component does not produce.

**Severity:** Low  
**Blocks Approval:** No  
**Recommended Action:** Same resolution path as Issue 1. If the architectural decision
is accepted by the reviewer, AC-12 scenario 6 should be acknowledged as partially satisfied
(the `<nav>` is tested; the `<footer>` is provided by Layout.tsx and is outside the
component's test boundary). No change to the test file is required unless the `<footer>`
is moved into the component.

---

### Issue 3 — Social Link Accessible Names Do Not Declare New-Tab Behaviour

**Description:** The design note recommends (but does not mandate) that social link
`aria-labels` append `"(opens in new tab)"` to inform screen reader users of new-tab
behaviour before activation. The current labels are `"Visit us on Facebook"`,
`"Visit us on X (Twitter)"`, `"Visit us on LinkedIn"` — informative and correct, but
do not include the new-tab signal.

**Severity:** Low  
**Blocks Approval:** No  
**Recommended Action:** Consider updating `aria-label` values to e.g. `"Visit us on
Facebook (opens in new tab)"` in a future iteration or as part of the CMS Configuration
validation pass. This is an accessibility enhancement, not a defect.

---

### Issue 4 — Sub-Component Files Registered in Component Map

**Description:** `generate-map` registers `footerTypes`, `footerLogo`, `footerNav`, and
`footerSocialLinks` as entries in `component-map.ts` alongside `SiteFooter`. These are
internal sub-components/types not intended to be CMS-addressable renderings. The same
pattern exists for the Header (`headerTypes`, `headerNav`, `headerLogo`), and this is
documented in the run report assumptions.

There is no functional impact (the entries will simply never be referenced by a Sitecore
rendering definition), but the map contains noise entries that may cause confusion.

**Severity:** Low  
**Blocks Approval:** No  
**Recommended Action:** The orchestrator and reviewer should be aware of this pattern.
If exclusions for camelCase sub-component files are desired, a future harness improvement
could configure `sitecore.cli.config.ts` to exclude camelCase-named files from the
component map scan (this was noted as a potential improvement in the implementation plan
but intentionally deferred without orchestrator approval).
