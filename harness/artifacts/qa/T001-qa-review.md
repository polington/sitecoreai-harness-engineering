## Design Alignment Review

**Structural alignment**: Good. The component hierarchy (Header → HeaderLogo + hamburger
button + HeaderNav) matches the design note's intended structure. The SXA composition
model is respected: `Layout.tsx` provides the `<header>` landmark and the
`headless-header` placeholder; `Header.tsx` renders inside that placeholder without
adding redundant wrapper elements.

**Visual system alignment**: Acceptable. The header uses Tailwind's utility system with
spacing values from the design system scale. A transparent background ensures the header
doesn't visually compete with page content. The navigation link styling (`text-sm
font-medium hover:underline`) follows the design system's "minimal and calm" aesthetic
with simple hover feedback (underline). Hamburger lines are rendered using `span` elements
with `bg-current` — inheriting colour from the text colour cascade, consistent with the
neutral-palette-first approach.

**Responsive behaviour**: Aligned. The `lg` (1024px) breakpoint used in the
implementation matches the design note's recommendation. Desktop nav is always visible
via `lg:flex`; mobile nav defaults to `hidden` and opens on hamburger click. The
hamburger button is hidden on desktop via `lg:hidden`. Responsive classes are applied
correctly following Tailwind v4 conventions.

**Accessibility**: Largely aligned. Semantic landmarks (`<header>` from Layout.tsx,
`<nav aria-label="Primary">` from headerNav) are in place. ARIA label on the hamburger
button is dynamic and descriptive. All interactive elements are keyboard-accessible. The
one partial gap is explicit focus-ring styling (AC-17 Warn above); this is a
correctness-level concern rather than a structural misalignment.

**Component pattern alignment**: Aligned. The three-file sub-component pattern
(types, logo, nav) with a camelCase naming convention — as defined in the implementation
plan — avoids polluting the Sitecore component map with unintended registrations. The
`Header.tsx` PascalCase entry is the only component map registration that Sitecore will
use. The `headerLogo`, `headerNav`, and `headerTypes` entries in the map are present
but harmless, as documented in the plan.

**One deviation noted**: The `headerNav` component returns `null` when `links` is empty
or undefined. This is intentional and matches the plan's instructions ("If links is empty
or undefined, render nothing"). It means the `<nav>` landmark does not exist in the DOM
when no navigation data is provided. This is an acceptable defensive behaviour for a
Sitecore rendering that may not always have a data source assigned; the design does not
require a fallback visible state.

## Issues Identified

### Issue 1 — Explicit focus ring missing from logo link and hamburger button

Description: `headerLogo.tsx`'s Next.js `<Link>` wrapper and `Header.tsx`'s hamburger
`<button>` carry no explicit `focus-visible` Tailwind classes. They rely on the browser's
default outline behaviour. Navigation links in `headerNav.tsx` have `focus:outline-none
focus-visible:ring-2 focus-visible:ring-current`, which removes the native outline and
replaces it with a custom ring — but the logo and button do not follow the same pattern.
This inconsistency means the focus ring appearance will differ across these elements.

Severity: Low  
Blocks approval: No

---

### Issue 2 — `<header>` semantic container provided by Layout.tsx, not Header.tsx

Description: AC-14 states "The header uses a `<header>` element as the outermost
semantic container." `Header.tsx` renders a `<div>` as its root. The `<header>` element
is provided by `Layout.tsx` which wraps the `headless-header` placeholder. The final
rendered output is semantically correct (exactly one `<header>` landmark), but a reader
inspecting `Header.tsx` in isolation would not see a `<header>` element and might
incorrectly conclude AC-14 is not met.

Severity: Low  
Blocks approval: No

The design note and implementation plan explicitly document this architectural decision and
the reasoning (avoiding nested `<header>` elements). Human reviewers should be aware
of this when evaluating AC-14.

---

### Issue 3 — `headerNav` not rendered when NavigationLinks is empty

Description: `headerNav.tsx` returns `null` when `links` is empty or undefined. This
means the `<nav aria-label="Primary">` landmark is absent from the DOM when no
navigation data is provided. A screen reader user navigating landmarks would not find
a navigation region. This is intentional defensive behaviour for a data-sourceless
rendering, and the spec does not require a fallback state.

Severity: Low  
Blocks approval: No
