## Acceptance Criteria Review

### AC-01 — Panel authoring and rendering
Status: Pass  
Notes: `Carousel.tsx` reads `fields?.Panels` and iterates over each item using `carouselPanel.tsx`. SDK primitives (`Image`, `Link`, `RichText`) are used for panel field rendering. Three-panel rendering is exercised implicitly by autoplay tests. Panel reordering and initial-panel selection are authoring operations handled via CMS data; the component consumes whatever panel array the CMS delivers. Minor gap: `fields.ActivePanel` is typed in `CarouselFields` but not read — the component always initializes `activeIndex` to `0`. The spec states "if omitted or invalid, the first available panel is active," which covers the default behavior; however, an authored non-zero initial panel is silently ignored.

---

### AC-02 — Navigation controls
Status: Pass  
Notes: `handlePrev` and `handleNext` implement wrap-around using modular arithmetic. Tests confirm forward wrap (last → first) and backward wrap (first → last). Controls are hidden when `isSingleOrEmpty` is true. Active indicator state is synchronized via `activeIndex`.

---

### AC-03 — Indicator controls
Status: Pass  
Notes: `carouselIndicators.tsx` renders one button per panel. `aria-pressed` reflects active state. Active indicator receives `bg-neutral-900` (darker treatment), inactive receives `bg-neutral-300`. Clicking an indicator calls `handleIndicatorSelect(index)`. Test confirms indicator click sets the correct active panel and updates `aria-pressed`.

---

### AC-04 — Autoplay default-off
Status: Pass  
Notes: `autoplayEnabled = fields?.Autoplay?.value === true` — defaults to `false`. Default `TransitionDelay` is 5000 ms when no value is authored. Tests confirm: no advancement without autoplay enabled; advancement fires at the configured 1000 ms delay when enabled. Play/pause button shown only when `autoplayEnabled` is true.

---

### AC-05 — Pause-on-hover
Status: Pass  
Notes: `pauseOnHover = fields?.PauseOnHover?.value !== false` defaults to `true`. `handleMouseEnter` sets `pauseSource` to `'hover'` only if it was `'none'`; `handleMouseLeave` clears `'hover'` back to `'none'`. Test confirms hover pauses advancement and unpauses on leave.

---

### AC-06 — Explicit user pause/resume
Status: Pass  
Notes: `handlePlayPause` sets `isPlaying=false, pauseSource='user'` on pause, and `isPlaying=true, pauseSource='none'` on resume. `handleMouseLeave` only transitions `'hover' → 'none'`, never touching `'user'`. Tests confirm user pause cannot be cleared by a subsequent mouse-leave event, and play resumes correctly.

---

### AC-07 — Document-hidden pause
Status: Warn  
Notes: The Page Visibility API listener is correctly implemented in a `useEffect`. When `visibilityState === 'hidden'`, `pauseSource` transitions `'none' → 'hidden'`; when visible again, it transitions `'hidden' → 'none'` only if the source was `'hidden'` (preserving user-pause through a hide/show cycle). **However, there is no automated test covering this behavior.** AC-18 explicitly requires `document-hidden` state coverage. The implementation plan documented the test approach (`Object.defineProperty + dispatchEvent`). This is a non-blocking gap — the behavior is implemented and verifiable manually — but the missing test reduces confidence.

---

### AC-08 — Panel title fallback
Status: Pass  
Notes: `carouselPanel.tsx` uses `title || "Slide ${index + 1} of ${total}"` for `aria-label`. `carouselIndicators.tsx` uses the same pattern for the indicator `aria-label` (`"Go to Slide N of M"`). Test confirms a panel without a title receives the generated label and the corresponding `role="group"` is findable by name.

---

### AC-09 — Keyboard operability
Status: Pass  
Notes: All controls (previous, next, play/pause, indicators) are rendered as standard `<button type="button">` elements. HTML buttons are inherently reachable via Tab and operable with Enter/Space. Focus is not managed explicitly — correct; focus follows natural browser behavior. `pointer-events-none` on inactive panels prevents invisible interactive elements from receiving pointer interaction, but keyboard focus on inactive panel content could theoretically be reached. In practice this is not an issue since inactive panels have `aria-hidden="true"` which removes them from the accessibility tree. No explicit keyboard-event test (`fireEvent.keyDown`) was written, which is acceptable given that button keyboard behavior is guaranteed by the HTML spec.

## Design Alignment Review

**Structural alignment — matches well.**  
The four-region structure defined in the design note (Stage, Control Row, Indicator Row, Panel Content) is faithfully implemented. The `VARIANT_CLASSES` map cleanly encodes the section, container, stage, controlRow, and indicatorRow class sets for each variant.

**Visual/system alignment — matches well.**  
Neutral palette (`bg-neutral-900` active, `bg-neutral-300` inactive) is consistent with the design system's neutral-dominant principle. Button style (rounded, `border-neutral-300`, minimal hover state) aligns with the design system's minimal button and visual restraint guidelines. No heavy shadows or decorative gradients — the panel overlay gradient (`bg-gradient-to-t from-black/70 to-transparent`) is functional (WCAG contrast for teaser text) not decorative.

**Responsive behavior — matches.**  
Default variant: contained layout with responsive padding (`px-4 sm:px-6 lg:px-8`) and height (`h-64 md:h-[500px]`). Hero/mini: full-bleed via `relative left-1/2 -translate-x-1/2 w-screen`. Hero indicator repositioning: `sm:justify-start sm:px-4`. All responsive rules use standard Tailwind breakpoints.

**Accessibility expectations — matches.**  
All ARIA roles, labels, and state attributes specified in the design note are present. Live region for panel-change announcements is implemented. Focus ring classes (`focus:ring-2 focus:ring-neutral-900 focus:ring-offset-2`) are on all interactive elements. `pointer-events-none` on inactive panels prevents invisible focus targets.

**One partial deviation — control row layout.**  
The design note states "Previous left, Next right" with the play/pause button between them. The `CarouselControls` component renders as a React fragment (Prev, optional Play/Pause, Next). The parent `<div className={classes.controlRow}>` uses `flex items-center justify-between` which places Prev at the far left and Next at the far right, with Play/Pause centered. This matches the design intent, but the `justify-between` only works as expected with the flex parent. The fragment approach is clean and correct.

**Panel content overlay — matches design note.**  
Semi-transparent gradient scrim (`from-black/70`) backing teaser text addresses the WCAG AA contrast requirement for overlay text noted in the design risks section.

## Issues Identified

**Issue 1 — Document-hidden state not tested**  
Description: The `visibilitychange` listener and `pauseSource='hidden'` state machine path are implemented but no automated test covers them. AC-07 and AC-18 both require this coverage.  
Severity: Medium  
Blocks approval: No  
Recommended action: Add a test using `Object.defineProperty(document, 'visibilityState', { value: 'hidden', writable: true })` and `document.dispatchEvent(new Event('visibilitychange'))` to verify the document-hidden pause behavior. This can be done in a follow-up without blocking CMS configuration.

---

**Issue 2 — ActivePanel authored field not consumed**  
Description: `CarouselFields` defines `ActivePanel?: Field<string>` but `Carousel.tsx` initializes `activeIndex` to `0` unconditionally. If an author sets an initial active panel in Sitecore, it is silently ignored. The spec states "if omitted or invalid, the first available panel is active" — the current implementation treats it as always omitted.  
Severity: Low  
Blocks approval: No  
Recommended action: Add `fields?.ActivePanel?.value` consumption to initialize `activeIndex` from authored data (with bounds checking) once the CMS template is available. A follow-up task or the CMS Configuration stage can flag this.

---

**Issue 3 — activeIndex not clamped when panels are reduced**  
Description: If panels are removed at authoring time such that `activeIndex >= panels.length`, optional chaining prevents crashes but `activePanel` will be `undefined`. The live region will show an empty string and no panel will appear active. This is a partial failure of AC-17 under adversarial authoring conditions.  
Severity: Low  
Blocks approval: No  
Recommended action: Add a `Math.min(activeIndex, totalPanels - 1)` normalization guard when computing the display active index, or add a `useEffect` to clamp state when `panels.length` changes.

---

**Issue 4 — typecheck not recorded in build evidence**  
Description: The implementation plan specifies `npm run typecheck` as a required validation step. The run report records lint and test results but not a typecheck pass. If the project does not have a distinct `typecheck` script, this should be confirmed and documented.  
Severity: Low  
Blocks approval: No  
Recommended action: Confirm whether `npm run typecheck` exists; if so, record the result in the run report. If not, document that type checking is covered via `tsc` invoked by the lint or build pipeline.

---

**Issue 5 — Variant tests assert CSS class names (testing standard note)**  
Description: Tests for AC-11–13 use `toContain('py-10')`, `toContain('w-screen')`, etc. The testing standard discourages testing CSS classes. These tests verify the variant selection decision (real behavior) but are coupled to the current class values.  
Severity: Low  
Blocks approval: No  
Recommended action: Informational only. The tests are acceptable as written but should be reviewed if variant classes are refactored.
