## Title

Carousel Component

---

## Feature Goal

Deliver a reusable, accessible Carousel component that presents an ordered sequence of content panels within the `headless-main` placeholder. The component must support previous/next navigation, indicator-driven panel selection, optional autoplay with pause controls, three presentation variants (default, hero, mini), and full keyboard and screen-reader accessibility.

---

## User Value

Site visitors benefit from an engaging, accessible panel-based presentation that highlights multiple pieces of content in a single visual stage. Content authors gain precise authoring control — defining panel order, selecting the initial active panel, configuring autoplay behavior, and choosing the visual treatment — without requiring developer intervention. This enables the home-page hero treatment and image-focused placements across the site from a single authored component.

---

## In Scope

- Ordered panel rendering with exactly one active panel visible at a time.
- Previous and next navigation controls that wrap from the first to the last panel and vice versa.
- Indicator controls (one per panel) that activate the corresponding panel and reflect selected state.
- Autoplay: configurable enable/disable, configurable delay (default 5 seconds), pause-on-hover (default enabled), explicit user pause/resume.
- Automatic advancement pauses when the document becomes hidden; resumes according to the current pause state when the document becomes visible again.
- A user-initiated pause is not silently undone by hover, focus, or document-visibility events.
- Panel deep-link addressing via stable fragment identifier when the target delivery platform supports URL fragments.
- Authoring operations: add, remove, edit, name, and reorder panels; select the initial active panel; configure autoplay, transition delay, pause-on-hover, and accessibility labels; select presentation variant.
- Three presentation variants:
  - `default`: relative-positioned stage, fade transitions, centered indicators below stage, previous/next controls aligned to control row.
  - `hero`: edge-to-edge presentation, no horizontal inset, extra spacing below carousel; on narrow screens indicators shift to left-aligned gutter position.
  - `mini`: edge-to-edge image stage approximately 400 px high, cover cropping with centered focal point.
- Responsive behavior: stage width follows its container; hero and mini variants remove side padding rather than shrinking content.
- Empty state: a carousel with no panels exposes an authoring empty state and suppresses navigation controls in the published view.
- Single-panel state: navigation controls and indicators are hidden or clearly inactive when there is only one panel or no panels.
- Panel without a title receives an unambiguous generated position label (e.g. "Panel 1").
- Accessible names for the carousel region and all interactive controls (previous, next, play, pause, indicators).
- Each panel exposes its position and active/inactive state to assistive technology.
- Keyboard operability: all controls are reachable and operable without a pointer device; focus is not trapped inside the carousel; automatic transitions do not unexpectedly move keyboard focus.
- The Carousel is placed in the `headless-main` placeholder on the home page, just before the footer, via Sitecore-authored route and layout data.
- Automated tests covering all required states and behaviors per the acceptance criteria.

---

## Out of Scope

- A new Carousel-specific content type or CMS content schema beyond what the component requires.
- A new image service or image processing pipeline.
- Platform-specific deployment, packaging, or build commands.
- Repository paths, component inheritance mechanisms, HTML attribute conventions, JavaScript hook names, or CSS selector conventions — these are implementation decisions.
- Custom animation libraries or third-party carousel plugins.
- Mock data, offline CMS fallback data, or local development data sources.
- Panel content types beyond those already supported by the delivery environment's content policy.
- Lazy-loading strategy for panel images (may be addressed by the existing image pipeline).

## Acceptance Criteria

### AC-01 — Panel authoring and rendering
A content author can create at least three panels, reorder them, select the initial active panel, and render the configured order in the published view. Panel content is sourced from Sitecore-authored route and layout data flowing through the existing placeholder and component-map composition model.

### AC-02 — Navigation controls
Clicking or activating Previous moves to the immediately preceding panel, wrapping from the first panel to the last. Clicking or activating Next moves to the immediately following panel, wrapping from the last panel to the first. The active panel indicator updates to reflect the new active panel after each navigation action. Controls are hidden or visually inactive when there is only one panel.

### AC-03 — Indicator controls
Each indicator corresponds to exactly one panel. Activating an indicator makes its panel active. The active indicator has a visually distinct state. The indicators are centered below the stage in the default variant.

### AC-04 — Autoplay default-off
Autoplay is disabled by default. When enabled, panels advance automatically after the configured transition delay. The default transition delay is 5 seconds when autoplay is enabled and no explicit delay is authored.

### AC-05 — Pause-on-hover
When autoplay is enabled and pause-on-hover is enabled (the default), pointer hover over the carousel pauses automatic advancement. Removing the pointer resumes advancement.

### AC-06 — Explicit user pause/resume
The carousel provides a play/pause control. Activating pause stops automatic advancement. A user-initiated pause is not undone by a subsequent hover, hover-leave, focus, or document-visibility event. Activating play resumes automatic advancement.

### AC-07 — Document-hidden pause
When the document becomes hidden (e.g. the user switches tabs), automatic advancement pauses. When the document becomes visible again, the carousel resumes according to its current play/pause state. Automatic transitions must not run while the document is hidden.

### AC-08 — Panel title fallback
A panel that has no authored title receives an unambiguous generated position label (e.g. "Slide 1 of 5"). Navigation and accessibility exposures use this label.

### AC-09 — Keyboard operability
All interactive controls (previous, next, play, pause, indicators) are reachable via keyboard tab/arrow navigation. Activating any control via keyboard produces the same outcome as pointer activation. Focus is not trapped inside the carousel. Automatic transitions do not move keyboard focus to a different element.

### AC-10 — Screen-reader accessibility
The carousel region has an accessible name. Each panel exposes its ordinal position and active/inactive state. Previous, next, play, pause, and indicator controls have accessible names. Activating an indicator or navigation control updates the accessible current-panel state.

### AC-11 — Default variant renders responsively
The default variant renders with a relative-positioned stage, fade transitions, centered indicators below the stage, and previous/next controls aligned to the control row. Stage width follows the containing layout.

### AC-12 — Hero variant renders responsively
The hero variant renders edge-to-edge with no horizontal inset and extra spacing below the carousel. On screens narrower than the breakpoint defined in the design system, the indicators shift to a left-aligned position aligned with the page gutter.

### AC-13 — Mini variant renders responsively
The mini variant renders edge-to-edge at approximately 400 px height, fills the available width, applies cover cropping, and keeps the image focal point centered. Stage width follows the containing layout.

### AC-14 — Active-panel transition behavior
Panel transitions use a visually restrained fade or equivalent low-distraction effect. Transitions must not delay keyboard activation, obscure the incoming panel, or move focus unexpectedly.

### AC-15 — Empty-panel state
A carousel with no panels renders an authoring empty state and does not display navigation controls or indicators in the published view.

### AC-16 — Single-panel state
A carousel with exactly one panel does not display previous/next controls or indicator dots, as there is no meaningful navigation destination.

### AC-17 — Authoring stability
Add, remove, edit, name, and reorder operations on panels must not corrupt the active-panel selection or the authored panel order.

### AC-18 — Automated test coverage (states)
Automated tests cover the following panel and playback states: inactive, active, transitioning, focus-visible, playing, hover-paused, user-paused, and document-hidden.

### AC-19 — Automated test coverage (behaviors)
Automated tests cover state transitions, autoplay and pause behavior, keyboard interaction, empty-panel behavior, single-panel behavior, and the three presentation variants.

### AC-20 — Placement
The Carousel component is placed in the `headless-main` placeholder on the home page at the position just before the footer, driven by Sitecore-authored route and layout data. It renders correctly within the existing placeholder and component-map composition model.

## Dependencies

- Sitecore XM Cloud route and layout data pipeline — the component is driven by authored content resolved through the existing JSS/headless route mechanism.
- The `headless-main` placeholder — must be registered and available on the home-page route.
- Component-map registration — the Carousel component must be included in the application's component map so it is resolved at render time.
- Panel content composition capability — panels may contain images, teasers, or other allowed content blocks already supported by the delivery environment's content policy.
- Stable panel identity mechanism — needed for active-state management, accessibility relationships, and optional deep linking.
- Client-side interaction capability — transitions and interactive state changes require a JavaScript execution context available in the delivery environment.
- Design system — layout tokens, breakpoints, and spacing values used by the three variants must be sourced from the project design system.

---

## Risks

- Autoplay and document-visibility interaction may differ subtly across browsers; the Page Visibility API behavior should be validated in the build phase.
- Keyboard focus management during animated transitions requires care; an incorrect implementation can cause WCAG 2.4.3 (Focus Order) violations.
- The hero variant's edge-to-edge behavior may conflict with existing layout container padding if the home-page layout uses a constrained-width wrapper; this should be confirmed during implementation planning.
- Indicator positioning change on narrow screens (hero variant) requires a verified breakpoint; if the design system does not define this breakpoint explicitly, a decision will be needed.
- A user-pause that survives all resume events (hover, visibility) may be unfamiliar to implementers; the test suite must explicitly verify this invariant.

## Open Questions

- Is there an existing panel/slot composition pattern in the current codebase (e.g. from the Promo Card Grid or Teaser components) that the Carousel panels should reuse, or will panel content use a fresh composition approach?
- Which image component or rendering helper should be used inside panels to ensure responsive cover cropping and focal-point preservation in the mini variant?
- Does the design system define the breakpoint at which the hero variant switches from centered to left-aligned indicators, or is this a new token to be introduced?
- Should the deep-link / URL-fragment behavior be treated as a progressive enhancement (no-op if fragments are not supported) or as a hard requirement for the delivery environment?
