## Title

Teaser Component

---

## Feature Goal

Provide a reusable content teaser rendering that combines optional imagery, editorial text, navigation, and calls to action, supporting multiple presentation variants and sourcing rules, and placed by content authors in the `headless-main` placeholder.

---

## User Value

Content authors gain a flexible, author-placed rendering that can represent featured articles, recent articles, adventures, cards, list items, hero content, and carousel slides — all from a single component. Authors can control imagery, copy, navigation, and visual treatment without developer intervention, while site visitors receive coherent, accessible, and responsive editorial content that clearly communicates destinations and content state.

---

## In Scope

### Content authoring

- Author can provide an optional image with alternative text or mark it decorative.
- Author can enter an optional pretitle, title, and rich-text description.
- Author can configure an optional primary destination link making the teaser navigable as a unit.
- Author can configure zero or more labeled call-to-action links, each with its own destination.
- Author can choose whether title, description, and image are sourced directly (authored values) or resolved from a linked content item.
- Author can select an allowed heading level for the title.
- Author can select one of the defined presentation variants: `default`, `featured`, `hero`, `card`, `list`, `slide`, or `secure`.
- Author can select image focal positioning (`imagetop` / `imagebottom`) where the selected variant requires it.

### Content sourcing rules

- Directly authored values take precedence unless sourcing from a linked content item is explicitly enabled.
- When title sourcing is enabled, the title is resolved from the linked content item.
- When description sourcing is enabled, the description is resolved from the linked content item.
- When image sourcing is enabled, the image is resolved from the linked content item, or from the current content item when no link is configured.

### Rendering behavior

- The teaser is registered as an available rendering for the `headless-main` placeholder.
- Missing optional fields are omitted without leaving broken labels, empty links, or reserved layout gaps.
- A teaser with no image, text, or action content produces the delivery environment's standard empty-component state rather than a misleading blank output.
- A primary link makes the teaser navigable as a unit only when there are no separate actions that would create ambiguous nested navigation.
- Each action is independently selectable with its own visible label and destination.
- The secure variant visually indicates restricted content with a restriction cue and communicates the state non-visually; it does not enforce access control.

### Presentation variants

- `default`: straightforward image and editorial layout with title, description, and optional action.
- `featured`: prominent split composition — large image region and narrower contrasting content pane; collapses to vertical stack on small screens.
- `hero`: large image stage with desktop overlay panel and stacked layout on small screens.
- `card`: compact image-forward block with clipped image area, bottom-aligned action, and pretitle badge; hover may zoom image and change action treatment.
- `list`: compact item with constrained image height, sans-serif bold uppercase title, and smaller gray uppercase supporting text.
- `slide`: tall image-backed composition for carousel use with lower-left content on large screens and centered/stacked on small screens.
- `secure`: visually muted treatment with restriction cue; subdued action treatment; does not enforce authorization.

### Accessibility

- Title uses a semantically appropriate heading level, selectable within the allowed range.
- Every non-decorative image exposes meaningful alternative text; decorative images are excluded from the accessibility tree.
- Link and action labels describe their destination or purpose without relying on surrounding visual styling alone.
- The component does not create ambiguous nested interactive elements.
- The secure variant communicates restricted state non-visually as well as visually.
- Rich-text descriptions preserve readable structure.

### Interactive states

- `static`: teaser with no destination presents editorial content without implying clickability.
- `linked default`: teaser with a primary destination makes the linked region visually discoverable with a meaningful accessible name.
- `hover`: linked content and actions provide visual affordance; hover must not be the only way to discover the destination.
- `focus-visible`: primary link and every action have a clear keyboard focus treatment that does not disappear in image-led or overlay layouts.
- `pressed/active`: activating a link or action gives normal browser feedback without altering layout or accidentally activating a second action.
- `multiple-actions`: each action has an independent focus and activation state; the primary link does not wrap or intercept action activation.
- `content-partial`: missing optional fields omitted with no empty heading, broken link, or reserved gap.
- `secure/restricted`: teaser is visually muted with restriction cue; communicates state in text or accessible metadata.
- `secure/available`: when access is available, the teaser must not remain visually disabled solely because it uses the secure variant.
- Narrow-screen states: linked regions and actions retain usable touch targets and visible focus/pressed feedback; overlay layouts move content into normal document flow.

### Testing

- Automated tests cover: static, linked, hover, focus-visible, pressed/active, multiple-action, partial-content, secure/restricted, secure/available, and narrow-screen interaction states.
- Automated tests cover: optional-field combinations, linked-content sourcing, multiple actions, image accessibility, navigation semantics, responsive variants, and secure-state communication.

---

## Out of Scope

- Page discovery or content search functionality.
- Authentication or access control enforcement — the teaser may signal restricted state but does not decide whether activation is permitted.
- Destination page rendering.
- A new image editing service or rich-text editing service.
- Design or implementation of a carousel container (the `slide` variant only defines the teaser's internal behavior when hosted inside one).
- Mock data or local development fallback data for CMS-offline scenarios — live CMS connectivity is assumed at all times.
- Partial Designs or header/footer placeholder composition — the teaser targets the `headless-main` placeholder placed by content authors.

## Acceptance Criteria

1. The Teaser Component rendering is registered and available for placement in the `headless-main` placeholder by a content author.

2. A content author can create a teaser with an image, title, description, and a primary destination link and render it as a coherent navigable unit — the entire teaser region is interactive, the title is visible, and the destination is reachable by keyboard and pointer.

3. A teaser configured with only a subset of optional fields (e.g., title only, or image and actions only) renders without broken markup, empty heading elements, broken link elements, or unexplained visual gaps in any variant.

4. When title sourcing is enabled, the title resolves from the linked content item's title field. When description sourcing is enabled, the description resolves from the linked content item's description field. When image sourcing is enabled, the image resolves from the linked content item's image, or from the current content item when no link is configured. Directly authored values take precedence when sourcing is disabled.

5. A teaser configured with multiple call-to-action links renders each action with its own distinct label, destination, visible focus state, and activation behavior — no action intercepts another, and the primary link does not wrap or intercept action activation.

6. Every non-decorative teaser image exposes a non-empty alternative text value accessible to assistive technology. An image marked decorative is excluded from the accessibility tree.

7. The title heading level is semantically valid HTML and matches the heading level selected by the author within the allowed design-system range.

8. All seven variants — `default`, `featured`, `hero`, `card`, `list`, `slide`, and `secure` — render and:
   - preserve the shared anatomy (image area, pretitle, title, description, action area);
   - apply the variant's defined layout geometry, spacing, typography, and image-cropping intent;
   - respond correctly at narrow viewports (the featured split collapses to vertical stack, the hero overlay moves to stacked flow, the slide content becomes centered/stacked, and card/list/secure remain legible in a narrow column).

9. Image focal positioning variants equivalent to `imagetop` and `imagebottom` are supported and affect image cropping without altering content order or link behavior.

10. No destination or content state is discoverable only through hover styling — all interactive states are also reachable and visible via keyboard focus and touch.

11. The secure variant renders with a visible restriction cue and communicates the restricted state in text or accessible metadata (not icon only); when the destination system indicates content is available, the teaser does not remain visually disabled.

12. A teaser with no image, text, or action content produces the delivery environment's standard empty-component output and not a misleading blank element.

13. The component passes automated tests covering all interaction states listed in scope: static, linked, hover, focus-visible, pressed/active, multiple-action, partial-content, secure/restricted, secure/available, and narrow-screen responsive states.

14. The component passes automated tests covering content variants: optional-field combinations, linked-content sourcing, multiple actions, image accessibility, navigation semantics, all responsive variants, and secure-state communication.

## Dependencies

- An image/content asset capability that supports alternative text, decorative state, and responsive delivery.
- A link/navigation capability for primary link and action destinations.
- Rich-text rendering and sanitization for the description field.
- Optional linked-content metadata resolution for title, description, and featured image sourcing.
- Heading-level policy from the delivery environment, defining the allowed heading hierarchy.
- An authorization/content-state signal available to the component when the secure presentation variant is used.
- The `headless-main` placeholder must exist and be configured to accept this rendering.

---

## Risks

- **Content sourcing precedence complexity**: the interaction between directly authored values and linked-content sourcing across three fields (title, description, image) creates several combinations that must all be handled consistently. Incomplete or incorrect sourcing resolution could produce silent content substitutions.
- **Variant layout scope**: seven distinct layout variants with different responsive behaviors increase the implementation surface. Incorrect responsive behavior for one variant may not be detected by testing of other variants.
- **Nested navigation ambiguity**: combining a primary link with multiple actions in an overlay or image-forward layout can create nested interactive elements that are difficult to make accessible. The interaction model must be precisely specified during design.
- **Secure variant misuse**: authors may apply the secure variant to content that is not actually restricted, producing a degraded presentation. The variant's visual cues must clearly indicate what the state means.
- **Rich-text rendering**: the description field renders rich text sourced from either authored content or a linked content item; the rendering pipeline must sanitize and constrain output to avoid markup injection or layout disruption.

---

## Open Questions

1. Is there a defined maximum number of call-to-action links per teaser, or is the `0..n` cardinality unbounded in practice? A practical upper bound may be needed to preserve layout coherence across all variants.
2. When image sourcing is enabled and no linked content item and no current content item image is available, what is the expected fallback — omit the image entirely, or render an empty image area?
3. Is the heading-level selection constrained to a fixed set of levels (e.g., h2–h4), or is the full h1–h6 range permissible? The design system's allowed range should be confirmed before implementation.
4. Does the `slide` variant require specific integration contracts with a carousel container (e.g., active/inactive state signals), or is the teaser entirely self-contained when placed inside one?
