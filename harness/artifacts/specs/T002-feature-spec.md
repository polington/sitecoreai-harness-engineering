## Title

Site Footer and Footer Partial Design

---

## Feature Goal

Deliver a fully authored, accessible Site Footer rendering together with the SXA Partial Design and Page Design configuration required to present it on every page of the site.

The feature establishes the footer as a distinct, reusable piece of page chrome: a new "Footer" Partial Design places the Site Footer rendering inside the `headless-footer` placeholder, and the existing "Default" Page Design is updated to reference that Partial Design so that all pages already using the Default design automatically gain the footer without per-page authoring.

---

## User Value

Site visitors see a consistent, accessible footer on every page that carries the site brand (logo), secondary navigation links, social media links, and copyright information.

- **Visitors** can orient themselves, navigate to secondary pages, and reach the organisation's social media channels from any page of the site.
- **Authors** can update the logo, navigation links, social links, and copyright text through Sitecore without requiring a code change.
- **Editors** benefit from a single data source item per site — changes propagate automatically to every page that uses the Default Page Design.
- **Maintainers** benefit from a clean separation of concerns: the footer lives in its own Partial Design, independent of the header, and can be versioned, replaced, or reused in additional Page Designs independently.

---

## In Scope

### 1. Site Footer Rendering

- The rendering is a new authored component backed by a dedicated Sitecore data source template.
- **Site logo** — rendered from an authored Sitecore Image field on the data source item; the logo image links to the site home page. The link target is the home page of the current site.
- **Secondary navigation links** — rendered from a Sitecore Link List field on the data source item. The list is authored (not hard-coded). Each item in the list renders as a visible, clickable link. The number and labels of links are controlled entirely by the authored field value.
- **Social media links** — three individual General Link fields on the data source template, one each for Facebook, X (Twitter), and LinkedIn. Each link opens in a new browser tab. Links are authored (not hard-coded). A link field that is left empty by the author must not render a broken or empty anchor element.
- **Copyright text** — rendered from a Single-Line Text field on the data source item. The full authored string is displayed as-is (no processing, no truncation).
- **Multi-column desktop layout** — three columns: logo column (left), secondary navigation column (centre), social links column (right). The layout is rendered using design system spacing and layout tokens.
- **Responsive stacking** — on mobile (at the design system's defined mobile breakpoint), the three columns collapse to a single stacked column. Column order when stacked: logo, navigation, social links.
- **Semantic HTML** — the footer uses a `<footer>` landmark element as its outermost wrapper. The secondary navigation link list is wrapped in a `<nav>` element with an appropriate `aria-label` (e.g. `aria-label="Footer navigation"`).
- **Keyboard accessibility** — all interactive elements (logo link, navigation links, social links) are reachable and activatable by keyboard. Tab order follows a logical reading order (logo → navigation links → social links).
- **Visible focus states** — all focusable elements within the footer display a visible focus indicator consistent with design system focus styling.
- **ARIA** — ARIA attributes are applied where semantic HTML alone is insufficient. Social link anchors include either visible text labels or `aria-label` values that identify the destination (e.g. `"Facebook"`, `"X (Twitter)"`, `"LinkedIn"`). Icon-only links must not be rendered without an accessible name.
- **Design system alignment** — the footer uses design system colour tokens, typography tokens, spacing scale values, and breakpoint definitions. No arbitrary style values are introduced.

### 2. SXA Footer Partial Design

- A new Sitecore Partial Design item named **"Footer"** is created under the site's `Presentation / Partial Designs` folder.
- The Footer Partial Design's layout places the Site Footer rendering in the **`headless-footer`** placeholder.
- The Site Footer rendering in the Partial Design is associated with a default or shared data source item so that a single authored data source drives the footer across all pages.
- No other renderings or placeholders are modified by this Partial Design.

### 3. Default Page Design Update

- The existing **"Default" Page Design** item is updated to reference the new Footer Partial Design in addition to any Partial Designs it already references (e.g. the Header Partial Design delivered by T001).
- The update must not remove or reorder any existing Partial Design references on the Default Page Design.
- After the update, all pages that use the Default Page Design render the footer in the `headless-footer` placeholder without requiring individual page re-authoring.

### 4. Tests

- Unit / component tests are provided for the Site Footer rendering covering:
  - Correct rendering of the logo image and its link to the home page.
  - Navigation links are rendered from the authored Link List field value (not hard-coded); the rendered output reflects the authored list.
  - Social links for Facebook, X (Twitter), and LinkedIn are rendered with `target="_blank"` and an accessible name.
  - A social link field that is empty does not render an anchor element.
  - Copyright text is rendered from the authored field value.
  - The footer uses a `<footer>` element and a `<nav>` element for navigation links.
  - On mobile (at the design system breakpoint), the layout applies single-column stacking classes.
- All tests pass.

  - The Site Footer data source template definition (all fields, field types, names, section).
  - The Site Footer rendering definition item (component name, data source template, allowed placeholders).
  - Placeholder settings update to allow the Site Footer rendering in the `headless-footer` placeholder.
  - Available Renderings entry for the Site Footer rendering.
  - Step-by-step instructions for creating the "Footer" Partial Design item and placing the Site Footer rendering in `headless-footer`.
  - Step-by-step instructions for updating the "Default" Page Design to reference the Footer Partial Design.
  - Serialization and validation steps.

## Out of Scope

- Changes to the Header Partial Design or any Partial Design other than the new "Footer" Partial Design.
- Additional social media platforms beyond Facebook, X (Twitter), and LinkedIn.
- Multi-section or mega-footer navigation (e.g. accordion groups, tabbed navigation, topic-grouped link columns).
- Language switcher, sitemap link, back-to-top button, or search functionality within the footer.
- Creation of or changes to any Page Design other than the existing "Default" Page Design.
- Personalization rules, A/B test variants, or conditional rendering on the footer, Footer Partial Design, or Default Page Design.
- Any changes to the Site Header rendering (delivered by T001) or the Header Partial Design.
- Dark mode or theme-switching support for the footer beyond what the design system token model already provides.
- Mock data, local CMS fallback data, or any offline-mode workaround — the application assumes live CMS connectivity at all times.

## Dependencies

- **Base SXA site** — the base SXA Headless site must already exist in the Sitecore content tree. No site scaffolding work is in scope for this task.
- **Design system tokens** — colour, typography, spacing, and breakpoint tokens must be available in the project for use by the footer component. These are assumed to be present from project setup.
- **`headless-footer` placeholder** — the `headless-footer` placeholder key must be registered in the head application's placeholder configuration. If it is absent, the footer rendering will not appear regardless of the Partial Design configuration. This was expected to be established as part of the B002 / T001 work.
- **"Default" Page Design item** — the "Default" Page Design must already exist in the Sitecore content tree. This is a prerequisite for the Page Design update step. If it does not exist, the CMS Configuration stage will be blocked.
- **Header Partial Design (T001)** — the existing reference(s) on the Default Page Design (Header Partial Design from T001, if present) must be preserved when updating the Page Design. The T001 Header Partial Design is a dependency only in the sense that it must not be disrupted, not that it must be implemented before this task begins.
- **SVG icon assets or icon library** — social media link icons (if icon-only presentation is chosen during Design) require SVG assets or an accessible icon library. Availability in the project must be confirmed during Implementation Planning.

## Risks

- **Default Page Design impact** — updating the "Default" Page Design to add the Footer Partial Design will affect the presentation of every page already authored against that design. Any page that previously had no footer region will gain one. This must be verified during QA to confirm no pages are adversely affected.
- **Placeholder key mismatch** — the `headless-footer` placeholder key used in the Footer Partial Design configuration must exactly match the key registered in the head application's placeholder configuration. A mismatch will silently prevent the footer from rendering. This must be verified during Implementation Planning and confirmed during CMS Configuration.
- **Route/layout data shape for navigation links** — the shape of the Sitecore layout data exposed to the head application for the Link List field should be confirmed during the Design and Implementation Planning stages to ensure it aligns with the approach used by the Site Header (T001). An undocumented or unexpected serialisation format could require component-level data transformation.
- **Icon assets availability** — if icon-only social links are chosen during Design, SVG icon assets or an icon library must be available in the project. If they are not, the Design stage must resolve this before Implementation Planning confirms the approach.
- **Social link accessible name approach** — if social link icons are used without visible text labels, the accessible name strategy (e.g. `aria-label` vs. visually hidden text) must be confirmed during Design so that it is consistently implemented and testable.

3. **Icon asset availability** — Are SVG icons for Facebook, X (Twitter), and LinkedIn already present in the project, or does the Implementation Plan need to account for adding them?
4. **Navigation link field type** — The task specifies a "Sitecore Link List field". 5. **Data source item location** — Should the Footer Partial Design reference a shared data source item located at a defined site-level path, or should it be an inline data source? The Implementation Plan should document the chosen approach and its authoring implications.
6. **Mobile breakpoint value** — The design system defines a mobile breakpoint but the specific pixel value is not enumerated in the design system document. The Design Note should confirm the exact token or value to be used for the responsive stacking behaviour.
