## Title

Site Header, Header Partial Design, and Default Page Design

---

## Feature Goal

Establish the foundational SXA presentation structure for the site and deliver the first
site-chrome component within it.

This task accomplishes three closely coupled things as a single delivery:

1. A **Header Partial Design** that defines shared page chrome — rendering the site header
   at the top and exposing `headless-main` and `headless-footer` placeholders for
   page-specific and future content.
2. A **Default Page Design** that composes the Header Partial Design, configured as the
   site's default Page Design and explicitly assigned to the home/root page so all pages
   inherit it automatically.
3. The **Site Header rendering** — authored logo linking to home, primary navigation
   driven by Sitecore route/layout data, and responsive mobile behaviour with a
   hamburger menu — placed inside the Header Partial Design.

---

## User Value

**For site visitors:** Every page on the site presents a consistent header with the
site logo and primary navigation. The header is accessible across input methods
(keyboard, pointer, touch) and works correctly at all viewport sizes including mobile.

**For content editors:** The header logo and navigation structure are Sitecore-authored
(not hard-coded), so editorial teams can update navigation content through the standard
Sitecore content management workflow without requiring a code change.

**For developers and future features:** The Default Page Design and Header Partial Design
provide the standard composition scaffold for all current and future pages. Subsequent
features (B003 footer, B004 hero, B005 rich text, etc.) slot into the exposed
placeholders without requiring a rework of page-level layout.

## In Scope

### SXA Partial Design — "Header"

- Create an SXA Partial Design item named **"Header"** under the site's
  `Presentation / Partial Designs` folder in the Sitecore content tree.
- The Header Partial Design layout must expose, in document order:
  - The Site Header rendering at the top of the layout.
  - A `headless-main` placeholder for page-specific rendered content.
  - A `headless-footer` placeholder reserved for the future footer rendering (empty
    for this task).
- The Partial Design item must be serialized in the repository's Sitecore content
  serialization configuration.

### SXA Page Design — "Default"

- Create an SXA Page Design item named **"Default"** under the site's
  `Presentation / Page Designs` folder in the Sitecore content tree.
- The Default Page Design must reference the Header Partial Design so that every page
  using this Page Design inherits the header and the standard placeholder structure.
- Configure the Default Page Design as the **site's default Page Design** so that
  newly created pages automatically inherit it.
- Explicitly assign the Default Page Design to the **site's home/root page** so that
  the home page and any existing pages without a Page Design assignment pick it up.
- The Page Design item must be serialized in the repository's Sitecore content
  serialization configuration.

### Site Header Rendering

- Implement the Site Header as a Next.js / JSS rendering component that is:
  - registered as a Sitecore rendering item with the appropriate component name.
  - placed inside the Header Partial Design in the SXA layout.
- The Site Header rendering must display an **authored site logo**:
  - The logo is sourced from a Sitecore Image field on the header data source item.
  - The logo links to the site's home page.
  - The Image field value (src, alt) is delivered via Sitecore layout/route data — not
    hard-coded.
- The Site Header rendering must display **primary navigation links**:
  - Links are sourced from Sitecore route/layout data (not hard-coded).
  - Each navigation item contains at minimum a display label and a URL derived from
    Sitecore content.
  - The component does not hard-code a fixed list of navigation destinations.
- The Site Header rendering must provide **responsive mobile behaviour**:
  - Above the defined breakpoint (as specified in the design system) the full
    navigation bar is visible.
  - Below the breakpoint a hamburger menu button is displayed.
  - Activating the hamburger button (click or Enter/Space key) opens the navigation
    menu.
  - Activating the button again closes the navigation menu.
  - The open/close state is managed within the component.
- The Site Header rendering must meet **accessibility requirements**:
  - The header region uses a semantic `<header>` element.
  - Navigation links are wrapped in a `<nav>` element with an appropriate ARIA label.
  - The hamburger toggle button has a descriptive ARIA label that reflects the
    open/closed state (e.g., "Open navigation" / "Close navigation").
  - All interactive elements are reachable and operable via keyboard Tab and
    Enter/Space.
  - Visible focus states are present on all interactive elements.
  - Typography, spacing, and colour tokens follow the project design system.
- The Site Header rendering must include a **Sitecore rendering item** definition and
  be registered in Available Renderings for the site so it can be placed in layouts.

### Component Tests

- Unit/component tests must cover:
  - The Site Header renders with a logo image and link when layout data supplies them.
  - The Site Header renders primary navigation links from layout data.
  - Below the breakpoint, the navigation menu is hidden by default and the hamburger
    button is visible.
  - Clicking the hamburger button opens the navigation menu.
  - Clicking the hamburger button again closes the navigation menu.
  - The hamburger button can be activated with the Enter key and the Space key.
  - All tests pass without failures or skipped assertions.

### Lint and Typecheck

- All changed or added source files must pass the project's lint configuration without
  new errors or warnings attributable to this feature.
- TypeScript typecheck must pass for all changed or added files.

### CMS Configuration Guide

- Produce a CMS Configuration Guide covering all steps needed to configure the
  Header Partial Design, Default Page Design, rendering item definitions, placeholder
  settings, available renderings entries, default Page Design assignment, and
  serialization steps in a clean Sitecore XM Cloud environment.

## Out of Scope

- The footer rendering itself (B003); only the empty `headless-footer` placeholder is
  wired up in the Header Partial Design.
- Additional Page Designs beyond "Default".
- Additional Partial Designs beyond "Header".
- Multi-level or mega-menu navigation beyond what the standard Sitecore route hierarchy
  provides for the primary navigation.
- Search box, language switcher, or utility navigation in the header.
- Personalization or A/B testing rules on the header, Partial Design, or Page Design.
- Any mock data, local development fallback data, or CMS-offline workarounds — this
  project assumes live CMS connectivity at all times.
- Dark mode styling (no design system dark mode tokens are defined for this task).

## Acceptance Criteria

### AC-01 — Header Partial Design exists

A Partial Design item named "Header" exists in the site's `Presentation / Partial Designs`
folder in the Sitecore content tree and is serialized in the repository.

### AC-02 — Header Partial Design placeholder structure

The Header Partial Design layout contains, in document order:
- the Site Header rendering at the top,
- a `headless-main` placeholder,
- a `headless-footer` placeholder.

A content editor inspecting the Header Partial Design layout in Sitecore can observe all
three elements in the layout definition.

### AC-03 — Default Page Design exists

A Page Design item named "Default" exists in the site's `Presentation / Page Designs`
folder in the Sitecore content tree and is serialized in the repository.

### AC-04 — Default Page Design references Header Partial Design

The "Default" Page Design references the "Header" Partial Design. Inspecting the
"Default" Page Design's Partial Designs field in Sitecore shows the "Header" Partial
Design is listed.

### AC-05 — Default Page Design is set as site default

The site's Page Design settings designate "Default" as the default Page Design. Newly
created pages under the site root inherit the "Default" Page Design without requiring
manual assignment.

### AC-06 — Default Page Design assigned to home/root page

The "Default" Page Design is explicitly assigned to the site's home/root page item.
Existing pages that had no Page Design assignment pick up the "Default" Page Design via
the site default.

### AC-07 — Site Header renders an authored logo

When the Site Header rendering is placed in the Header Partial Design layout and a
Sitecore Image field value is authored on the data source item, the logo image is
rendered in the header with the correct `src` and `alt` values sourced from Sitecore
layout data. The logo image is wrapped in an anchor element that links to the site home
page.

### AC-08 — Logo image and link sourced from Sitecore layout data

The logo `src`, `alt`, and link destination are not hard-coded. They are driven by
Sitecore Image field data delivered through the JSS layout/route data pipeline. A
change to the authored Image field value is reflected in the rendered output without a
code change.

### AC-09 — Site Header renders primary navigation from Sitecore data

The Site Header renders navigation links whose labels and URLs are sourced from Sitecore
route/layout data. The component does not contain a hard-coded list of navigation
destinations. The links rendered correspond to the navigation items provided in the
layout data for the page.

### AC-10 — Responsive: navigation visible at desktop breakpoint

At or above the desktop breakpoint defined in the design system, the primary navigation
links are visible in the header without requiring any user interaction.

### AC-11 — Responsive: hamburger menu displayed at mobile breakpoint

Below the desktop breakpoint, the primary navigation links are hidden by default and a
hamburger menu button is displayed.

### AC-12 — Hamburger menu opens and closes via pointer

Clicking the hamburger button opens the navigation menu (making navigation links
visible). Clicking the hamburger button again closes the navigation menu.

### AC-13 — Hamburger menu opens and closes via keyboard

Pressing Enter or Space while the hamburger button is focused opens the navigation menu.
Pressing Enter or Space again closes the navigation menu.

### AC-14 — Semantic HTML structure

The header uses a `<header>` element as the outermost semantic container. Navigation
links are wrapped in a `<nav>` element.

### AC-15 — Hamburger button ARIA label reflects state

The hamburger toggle button carries an ARIA label that describes its current action (e.g.,
"Open navigation" when the menu is closed, "Close navigation" when the menu is open).

### AC-16 — Keyboard accessibility

All interactive elements in the Site Header (logo link, navigation links, hamburger
button) are reachable via keyboard Tab navigation and can be activated via Enter/Space
as appropriate.

### AC-17 — Visible focus states

All interactive elements in the Site Header display a visible focus indicator when
focused by keyboard. Focus indicators conform to the design system's focus styling.

### AC-18 — Design system alignment

The Site Header uses typography, colour, and spacing tokens from the project design system.
No arbitrary values are introduced for properties that have design-system equivalents.

### AC-19 — Component tests pass

All component tests for the Site Header pass. Tests cover: logo rendering with layout
data, navigation link rendering from layout data, mobile menu hidden by default,
hamburger opens menu, hamburger closes menu, keyboard activation of hamburger.

### AC-20 — Lint and typecheck pass

Running the project lint and TypeScript typecheck commands produces no new errors or
warnings attributable to files created or modified in this task.

### AC-21 — CMS Configuration Guide produced

A CMS Configuration Guide artifact exists at `harness/artifacts/cms-config/T001-cms-config.md`
and fully describes how to recreate the Header Partial Design, the Default Page Design,
the rendering item definitions, placeholder settings, available renderings registration,
default Page Design assignment, home page assignment, and serialization steps in a clean
Sitecore XM Cloud environment.

## Risks

- **Partial Design / Page Design content tree paths**: If the site's `Presentation`
  folder structure differs from the SXA defaults, the CMS Configuration Guide must
  document the actual paths used rather than assumed defaults.
- **Existing Page Design on home page**: The home/root page may already have a Page
  Design assigned. Overwriting or replacing it must be handled deliberately; the CMS
  Configuration Guide must call out this risk explicitly.
- **Route/layout data shape for navigation**: Primary navigation behaviour depends on
  the shape of the Sitecore route data exposed to the JSS head application. If the
  expected navigation field or structure is not confirmed during Design and
  Implementation Planning, the navigation implementation may need adjustment.
- **Serialization scope**: New Partial Design and Page Design items must be within the
  scope of the existing serialization configuration. If they are not, the serialization
  configuration must be extended, which is a prerequisite for committing the content
  items.
- **Breakpoint values**: The design system document describes a responsive breakpoint
  concept but does not provide specific pixel values. The Implementation Planning stage
  should confirm the breakpoint token or value to use for the mobile/desktop transition.

## Open Questions

1. **Navigation data shape**: What is the exact shape of the Sitecore layout/route data
   that provides primary navigation items to the JSS head application? Is it a
   dedicated navigation rendering's fields, a list of child-page links derived from the
   route tree, or another structure? This should be confirmed or defined during the
   Design stage.

2. **Breakpoint value**: The design system defines a responsive design requirement but
   does not specify a concrete breakpoint pixel value for the mobile/desktop transition.
   The Implementation Planning stage should confirm or define this value (e.g., 768px,
   1024px) so tests and implementation are aligned.

3. **Logo field type and data source template**: Is the logo sourced from a data source
   item on the header rendering itself (a specific template), or from a site settings
   item? The Design or Implementation Planning stage should define the data source
   template and field structure.

4. **Serialization path**: Are the Partial Designs and Page Design folders already
   within the configured serialization scope, or does the serialization configuration
   need to be extended for this task?
