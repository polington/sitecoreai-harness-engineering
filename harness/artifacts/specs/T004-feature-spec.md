## Title

Hero Banner Component

---

## Feature Goal

Deliver a hero banner rendering component that content authors can place in the `headless-main` placeholder. The hero banner displays an authored heading, subheading, full-width background image, and an optional call-to-action link, with an author-configurable semi-transparent dark overlay to ensure text readability.

---

## User Value

The hero banner gives content authors a prominent, visually impactful page element for communicating key messages. It is the first component available for direct placement in the main content area by authors, establishing the pattern for future author-placed renderings. The configurable overlay opacity lets authors balance visual impact with text readability without developer intervention.

---

## In Scope

- A Next.js rendering component named **HeroBanner** that renders the following authored fields:
  - **Heading** — Sitecore Single-Line Text field, rendered as an `<h1>` element.
  - **Subheading** — Sitecore Single-Line Text field, rendered below the heading.
  - **Background Image** — Sitecore Image field, rendered as a full-width, fixed-height background using Next.js Image optimisation where feasible, with a CSS background-image fallback if Image component constraints prevent full-width rendering.
  - **CTA Link** — Sitecore General Link field, rendered as a styled button/link below the subheading. When the link field is empty, no CTA element is rendered.
  - **Overlay Opacity** — Sitecore field (Droplink or Number field) controlling the opacity of a semi-transparent dark overlay/scrim applied over the background image. Must default to a sensible value (40–50% opacity) so the hero is usable immediately after authoring.

- Layout and visual behaviour:
  - Full-width layout that spans the full viewport width regardless of parent container constraints.
  - Fixed height of approximately `60vh`, consistent across viewport sizes.
  - Centre-aligned text overlay (heading, subheading, and CTA) positioned over the background image.
  - Semi-transparent dark overlay/scrim applied between the background image and text content.
  - Responsive text sizing: text scales down for mobile viewports while maintaining readability and centre-aligned layout.

- Alignment with project design system tokens (typography, spacing, colour, breakpoints).

- Accessibility:
  - Semantic HTML markup (heading hierarchy, appropriate link element for CTA).
  - Meaningful `alt` text on the background image sourced from the Sitecore Image field's alt text property, with the option for authors to leave it empty for decorative images.
  - Sufficient colour contrast between overlay text and the scrim.
  - Keyboard-focusable CTA link with visible focus states.
  - ARIA attributes where required to support assistive technology.

- Sitecore CMS configuration:
  - A data source template for the Hero Banner containing fields for heading, subheading, background image, CTA link, and overlay opacity.
  - Registration of the Hero Banner rendering as an available rendering for the `headless-main` placeholder.
  - Serialization of all new Sitecore items.

- Component tests covering:
  - Rendering with all fields populated.
  - Rendering without the optional CTA link (CTA is absent from output).
  - Overlay scrim presence in the rendered output.
  - Responsive/mobile text scaling behaviour.

- A CMS Configuration Guide describing how to recreate the Hero Banner rendering definition, data source template, placeholder settings, available renderings entry, and serialization in a clean Sitecore environment.

---

## Out of Scope

- Video or animated backgrounds.
- Multiple CTA buttons (only a single optional CTA is supported).
- Configurable text alignment (text is always centre-aligned).
- Carousel or slideshow behaviour (single static hero only).
- Parallax scrolling effects on the background image.
- Content personalisation or A/B testing rules on the hero banner.
- Animation or transition effects on text/CTA appearance.
- Additional hero banner variants or layout options beyond the single full-width design.
- Configurable heading level (heading is always `<h1>`).
- Mock data, local development fallback data, or CMS-offline workarounds.

---

## Acceptance Criteria

1. The Hero Banner rendering is registered as an available rendering for the `headless-main` placeholder in Sitecore.

2. A data source template exists in Sitecore with fields for heading (Single-Line Text), subheading (Single-Line Text), background image (Image), CTA link (General Link), and overlay opacity.

3. When all fields are authored, the Hero Banner renders an `<h1>` heading, a subheading, a background image, a semi-transparent dark overlay, and a styled CTA link/button.

4. When the CTA link field is empty, no CTA element (button, anchor, or empty wrapper) is rendered in the DOM.

5. The background image renders at full viewport width and a fixed height of approximately `60vh`, scaling responsively without distortion (using `object-fit: cover` or equivalent).

6. The hero banner spans the full viewport width regardless of parent container constraints.

7. A semi-transparent dark overlay/scrim is rendered between the background image and the text content.

8. The overlay opacity reflects the value authored in the overlay opacity field. When no value is authored, the overlay defaults to 40–50% opacity.

9. The heading, subheading, and CTA are centre-aligned horizontally and vertically centred within the banner area.

10. Text sizes scale down on mobile viewports (below the design system's mobile breakpoint) while remaining readable.

11. The background image carries an `alt` attribute sourced from the Sitecore Image field's alt text property. When the alt text is empty, the image is treated as decorative (empty `alt=""`).

12. The CTA link is keyboard-focusable and has a visible focus state that meets WCAG 2.1 AA contrast requirements.

13. The rendered markup uses semantic HTML: `<h1>` for the heading, an appropriate element for the subheading, and an `<a>` element for the CTA link.

14. Component tests exist and pass for: rendering with all fields populated, rendering without the CTA link, and overlay scrim presence.

15. All changed code passes lint (`eslint`) and type checking (`tsc --noEmit`) with no new errors.

16. All new Sitecore items (data source template, rendering definition, placeholder settings entries, available renderings entries) are serialized and committed.

17. A CMS Configuration Guide is produced that describes how to recreate the Hero Banner rendering definition, data source template, placeholder settings, available renderings entry, and serialization steps in a clean Sitecore environment.

---

## Risks

- **Full-width breakout styling conflicts**: The full-width layout that breaks out of parent container constraints may conflict with the existing page layout structure. This should be confirmed during the Design stage.
- **Next.js Image component constraints**: The Next.js Image component's fixed-dimension and layout-mode requirements may complicate the full-width background image approach. A CSS background-image fallback strategy should be evaluated during Implementation Planning.
- **Low overlay opacity values**: Author-configurable overlay opacity introduces the risk of editors setting very low opacity values that result in poor text contrast. The implementation should enforce a sensible minimum value or provide clear guidance in the CMS Configuration Guide.
- **Background image alt text strategy**: The approach to alt text (meaningful vs. decorative) depends on how authors use the hero banner. The Design stage should confirm the recommended approach and ensure authors can control decorative vs. meaningful alt text through the existing Sitecore Image field alt property.

---

## Open Questions

1. Should the overlay opacity field enforce a minimum value programmatically (e.g. never below 30%) to prevent authors from creating inaccessible contrast, or should this be handled purely through editorial guidance in the CMS Configuration Guide?

2. Should the hero banner's fixed height (`60vh`) be a design-system token or a component-level constant? This should be decided during the Design stage.

3. Should the subheading use a `<p>` element or an `<h2>` element? The heading hierarchy implications should be confirmed during Design, considering that the hero heading is an `<h1>` and subsequent page content sections will also need heading levels.
