## Title

Automated CI/CD Testing — Pull Request Validation Workflow

---

## Feature Goal

Create a GitHub Actions workflow that automatically validates code quality on every pull request by running the existing test suite, linter, and type checker against the head application, preventing regressions from being merged.

---

## User Value

Developers contributing to the head application receive immediate, automated feedback when a pull request introduces test failures, lint errors, or type errors. This catches regressions before code review, reduces manual validation effort, and ensures the main branch maintains a consistent quality baseline.

---

## In Scope

- A single GitHub Actions workflow file at `.github/workflows/ci.yml`.
- The workflow triggers on `pull_request` events (types: `opened`, `synchronize`, `reopened`) targeting the default branch.
- The workflow checks out the repository.
- The workflow sets up Node.js at the version used by the project.
- The workflow installs dependencies for the head application at `src/headapps/rob-harness-engineering/`.
- The workflow uses dependency caching (npm cache) to speed up subsequent runs.
- The workflow runs the Jest test suite and fails the job if any test fails.
- The workflow runs ESLint and fails the job if any lint error is reported.
- The workflow runs the TypeScript compiler in `--noEmit` mode and fails the job if any type error is reported.
- All commands are scoped to the head application's working directory.
- Documentation of recommended branch protection rules to require these checks before merge.

---

## Out of Scope

- End-to-end or integration testing (Playwright, Cypress, etc.).
- Deployment pipelines (CD to staging or production).
- Docker or container-based builds.
- Testing of the Sitecore platform project or serialized items.
- Adding new tests or modifying existing test coverage.
- Enforcing branch protection rules in repository settings (documentation only).
- Notification integrations (Slack, Teams, email).
- Matrix builds across multiple Node.js versions.
- Private npm registry authentication configuration (flag as a risk if needed).
- Mock data, local development fallback data, or CMS-offline workarounds.

---

## Acceptance Criteria

1. A GitHub Actions workflow file exists at `.github/workflows/ci.yml` and is valid YAML.
2. The workflow triggers automatically when a pull request is opened, updated (synchronize), or reopened against the default branch.
3. The workflow checks out the repository using `actions/checkout`.
4. The workflow sets up Node.js using `actions/setup-node` at the version defined by the project's configuration.
5. The workflow uses dependency caching (e.g., npm cache via `actions/setup-node` cache option or `actions/cache`) so that repeated runs avoid redundant dependency downloads.
6. The workflow installs the head application's dependencies scoped to `src/headapps/rob-harness-engineering/`.
7. The workflow runs the full Jest test suite; the job fails if any test fails.
8. The workflow runs ESLint; the job fails if any lint error is reported.
9. The workflow runs the TypeScript compiler in `--noEmit` mode; the job fails if any type error is reported.
10. When all checks pass, the workflow completes with a success (green) status.
11. When any check fails, the workflow reports a clear failure (red) status with actionable output identifying which step failed.
12. Documentation exists describing how to configure branch protection rules in the GitHub repository settings to require the workflow checks before merge.

## Risks

- If the existing test suite contains flaky or environment-dependent tests, the CI workflow may produce false failures. This should be identified during QA.
- The working directory for npm commands must be correctly set to `src/headapps/rob-harness-engineering/`; an incorrect path will cause all steps to fail silently or with misleading errors.
- If the project uses private npm registries or scoped packages requiring authentication, the workflow will need registry credentials configured as GitHub secrets. This should be confirmed during Implementation Planning by inspecting `package.json` and any `.npmrc` configuration.
- GitHub Actions minutes may be limited on the repository's plan; the workflow should be efficient to minimize usage.
