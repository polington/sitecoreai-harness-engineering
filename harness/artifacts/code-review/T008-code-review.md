## Review Findings

### Finding 1 — Collapsed Panel Not Removed from Keyboard Tab Order

**File:** `src/headapps/rob-harness-engineering/src/components/Accordion/accordionItem.tsx`  
**Line:** ~33–44 (panel wrapper `<div>`)  
**Severity:** Major  
**Description:** The panel wrapper uses `aria-hidden={!isOpen}` to hide collapsed panels from the screen reader tree. However, `aria-hidden="true"` does not remove descendant elements from the keyboard tab order. Any interactive elements rendered inside a collapsed panel by `RichText` (e.g., anchor links) remain focusable via Tab even though the panel is visually zero-height and removed from the accessibility tree. Keyboard users can therefore Tab into invisible, inaccessible content — a recognized WCAG 2.1 SC 2.1.1 / SC 2.4.3 failure pattern. The design note specifies that "collapsed panels must be removed from the accessibility tree and normal tab order" (AC 19). This finding was raised in the QA Review as Issue 1 and remains unresolved in the current code.  
**Suggested Fix:** Add the `inert` attribute to the panel wrapper div. `inert` prevents focus, pointer events, and find-in-page on all descendants without affecting CSS visibility or the ongoing grid transition. Apply it when the panel is collapsed:

```tsx
<div
  id={panelId}
  role="region"
  aria-labelledby={headerId}
  aria-hidden={!isOpen}
  {...(!isOpen ? { inert: '' } : {})}
  className={`grid transition-all duration-200 ease-in-out ${isOpen ? 'grid-rows-[1fr]' : 'grid-rows-[0fr]'}`}
>
```

Use the spread form `{...(!isOpen ? { inert: '' } : {})}` to avoid TypeScript type errors if the project's React type definitions do not yet declare `inert` as a recognized JSX prop. The `inert` attribute is supported in all modern browsers (Chrome 102+, Firefox 112+, Safari 15.5+).

### Finding 2 — Title Font Scale One Step Below H4 Target

**File:** `src/headapps/rob-harness-engineering/src/components/Accordion/accordionItem.tsx`  
**Line:** ~25 (button `className` string)  
**Severity:** Minor  
**Description:** The button uses `text-lg` (18 px in Tailwind's default scale) for the item title. The design note specifies "approximately H4 scale (~20–22 px per design system heading scale)." The design system lists H4 at 20–22 px; `text-xl` (20 px) aligns with the lower bound of that range. `text-lg` is one step below the specified scale. This was raised in the QA Review as Issue 2 and remains unresolved.  
**Suggested Fix:** Replace `text-lg` with `text-xl` in the button's `className` string on line ~25 of `accordionItem.tsx`.

Before:
```tsx
className="w-full flex justify-between items-start py-4 px-0 text-left font-bold uppercase text-lg hover:opacity-75 ..."
```

After:
```tsx
className="w-full flex justify-between items-start py-4 px-0 text-left font-bold uppercase text-xl hover:opacity-75 ..."
```

### Finding 3 — Hover State Not Covered by a Test

**File:** `src/headapps/rob-harness-engineering/src/components/Accordion/__tests__/Accordion.test.tsx`  
**Line:** N/A — missing test  
**Severity:** Minor  
**Description:** AC 26 explicitly lists "hover" as a required test state. All other states in AC 26 are covered by the existing 25 tests, but there is no hover test. The hover treatment is `hover:opacity-75` on the header button — a pure CSS pseudo-class with no JavaScript behavior. While the testing standard says "Avoid testing CSS classes," the existing test "header button has focus-visible styling class" already applies a class-presence assertion for the analogous focus-visible state. Adding a parallel hover class-presence test would close the literal AC 26 gap using the same established pattern. This finding was raised in the QA Review as Issue 3 and remains unresolved.  
**Suggested Fix:** Add the following test to `Accordion.test.tsx`, grouped with the focus-visible test:

```tsx
it('header button has hover styling class', () => {
  render(<Accordion fields={{ Items: ITEMS }} />);
  const button = screen.getAllByRole('button')[0];
  expect(button.className).toContain('hover:opacity-75');
});
```
