## Title

Hero Banner Component

---

## Feature Overview

The Hero Banner is a full-width, fixed-height rendering component placed in the `headless-main` placeholder. It displays an authored heading, subheading, and background image with a semi-transparent dark overlay (scrim) to ensure text readability. An optional call-to-action link appears as a styled button below the subheading. All content — including the overlay opacity — is author-controlled through a Sitecore data source item.

This is the first author-placed rendering designed for the `headless-main` placeholder, establishing the pattern for future content components that authors compose into pages.

---

## Design Intent

**Visual impact without excess.** The hero banner should feel bold and prominent — it is a page-leading element — but must remain within the design system's principle of visual restraint. The background image and overlay do the visual work; typography and spacing maintain the calm, content-driven aesthetic.

**Author control.** Content authors fully control the heading, subheading, background image, CTA, and overlay opacity. No hard-coded content appears in the component. When a field is absent or empty, the component gracefully omits that element rather than rendering an empty shell.

**Readability through the scrim.** The semi-transparent dark overlay between the background image and text content is the primary mechanism for ensuring text contrast. The overlay opacity is author-configurable with a sensible default (40–50%), so the hero is immediately usable after authoring without a developer needing to tune contrast.

**Full-width breakout.** The hero banner spans the full viewport width regardless of any parent container constraints introduced by the page layout. This is a deliberate departure from the standard contained content width, giving the hero its visual prominence.

**Accessibility as structure.** Semantic heading markup, meaningful or decorative alt text for the background image, keyboard-focusable CTA with visible focus state, and sufficient colour contrast are structural requirements built into the design, not deferred to QA.

**Design system alignment.** Typography scale, spacing tokens, breakpoint definitions, and interaction patterns (hover, focus) are drawn from the project design system. No arbitrary values are introduced.

## Page / Feature Structure

The Hero Banner is a single rendering placed inside the `headless-main` placeholder. It occupies the full viewport width and a fixed height of approximately `60vh`. It is not a page-level layout element like the header or footer — it is a content-area component that authors add to individual pages.

The component's visual structure is a layered stack:

```
┌──────────────────────────────────────────────────────────────────┐
│  Background Image (full-width, fixed-height, object-fit: cover) │
│  ┌────────────────────────────────────────────────────────────┐  │
│  │  Semi-transparent dark overlay / scrim                     │  │
│  │  ┌──────────────────────────────────────────────────────┐  │  │
│  │  │            [ Heading — <h1> ]                        │  │  │
│  │  │            [ Subheading ]                            │  │  │
│  │  │            [ CTA Button/Link ] (optional)            │  │  │
│  │  └──────────────────────────────────────────────────────┘  │  │
│  └────────────────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────────────────┘
```

The three layers, back to front:

1. **Background image** — fills the entire banner area, cropped via `object-fit: cover` to prevent distortion.
2. **Overlay scrim** — a semi-transparent dark layer sitting on top of the image, behind the text. Opacity is author-configurable.
3. **Text content region** — heading, subheading, and optional CTA, centre-aligned both horizontally and vertically within the banner.

---

## Section Breakdown

### Background Image Layer

**Purpose:** Provide a visually impactful photographic or illustrative backdrop for the hero message.

**Expected content:** A single Sitecore Image field. The image is rendered at full viewport width and the banner's fixed height (`60vh`), using `object-fit: cover` to fill the space without distortion. The image should be optimised for web delivery using Next.js Image optimisation where feasible; if the Next.js Image component's layout constraints prevent reliable full-width rendering, a CSS background-image approach is an acceptable fallback.

**Alt text behaviour:** The image carries an `alt` attribute sourced from the Sitecore Image field's alt text property. When the author provides alt text, it is used directly (meaningful image). When the author leaves the alt text empty, the image is treated as decorative (`alt=""`). This gives authors explicit control over whether the background image is announced to screen readers.

**Visual guidance:** The image must fill the banner area edge-to-edge with no visible letterboxing, padding, or gaps. The `cover` fit behaviour ensures the image scales up or down to cover the full area, cropping edges as needed to maintain aspect ratio.

---

### Overlay Scrim Layer

**Purpose:** Create a darkened layer between the background image and the text content to ensure text is readable regardless of the background image's lightness or visual complexity.

**Expected content:** A solid dark-coloured overlay (black or near-black from the design system's neutral palette) applied at a configurable opacity level. The overlay covers the entire banner area, matching the dimensions of the background image exactly.

**Author-configurable opacity:** The overlay opacity is controlled by a Sitecore field on the data source item. The field should offer a constrained set of values or a numeric range. The default opacity when no value is authored should be 40–50%, making the hero immediately usable.

**Design recommendation on minimum opacity:** To prevent authors from inadvertently creating inaccessible contrast, the component should enforce a minimum overlay opacity of 30%. Values below this threshold produce insufficient contrast for white text on most photographic backgrounds. This enforcement should be programmatic (in the component logic), not purely editorial guidance.

**Visual guidance:** The scrim should be visually smooth and uniform — no gradients, patterns, or directional fades. A simple flat semi-transparent layer is the intended design.

---

### Text Content Region

**Purpose:** Deliver the hero message — heading, subheading, and optional CTA — in a clearly readable, centred composition over the background image and scrim.

**Layout:** The text content region is centred both horizontally and vertically within the banner area. Content is stacked vertically: heading on top, subheading below, CTA (when present) below the subheading. The vertical stack should use design system spacing tokens between elements.

---

#### Heading

**Expected content:** A single-line text string from the Sitecore Single-Line Text field, rendered as an `<h1>` element.

**Visual guidance:** The heading is the primary visual anchor of the hero. It should use the design system's H1 scale (36–48px on desktop) in white or a high-contrast light colour against the dark scrim. Font weight should be bold or semi-bold for visual prominence.

**Semantic note:** The heading is always `<h1>`. This is appropriate because the hero banner is expected to be the leading content element on a page where it is used. Pages using the hero banner should not place a second `<h1>` elsewhere on the page.

---

#### Subheading

**Expected content:** A single-line text string from a Sitecore Single-Line Text field, rendered below the heading.

**Element choice:** The subheading should use a `<p>` element, not an `<h2>`. The subheading is a supporting descriptive line for the hero heading, not a structural section heading in the page outline. Using `<p>` preserves the heading hierarchy for subsequent page sections, which will appropriately use `<h2>` and below.

**Visual guidance:** The subheading should use the design system's body or large body text scale (18–24px on desktop) in white or a high-contrast light colour. It should be visually subordinate to the heading — smaller size, potentially lighter weight. Spacing between the heading and subheading should use a design system token (e.g. 16–24px).

---

#### CTA Link/Button

**Expected content:** A single optional link from the Sitecore General Link field. When the field is populated, a styled link is rendered. When the field is empty, no element is rendered — no empty anchor, no placeholder button, no empty wrapper.

**Visual guidance:** The CTA should be styled as a button-like element — a visible, distinct call-to-action that stands out from the heading and subheading text. It should use a solid or outlined style with sufficient contrast against the dark scrim. The recommended approach is a light/white button with dark text, or a bordered/outlined light button, to contrast with the dark overlay. The button style should follow the design system's minimal button pattern.

**Spacing:** The CTA is separated from the subheading by a design system spacing token (e.g. 24–32px), providing clear visual separation.

**Interaction:**
- Hover: a subtle visual change (background shift, border change, or slight opacity change) consistent with the design system's interaction model.
- Focus: a clearly visible focus ring that meets WCAG 2.1 AA contrast requirements. The focus indicator must be visible against the dark scrim background.
- Activation: standard anchor link behaviour — navigates to the authored URL on click or keyboard Enter.

## Component Recommendations

**HeroBanner** — the top-level rendering component. Wraps the entire hero in a semantic container element. Receives all field data (heading, subheading, background image, CTA link, overlay opacity) from Sitecore layout data via component props. Responsible for the full-width breakout styling, fixed height, and layered composition of background image, scrim, and text content.

**No sub-components are recommended.** The hero banner's internal structure (image, overlay, text stack) is simple enough to be rendered directly within the single HeroBanner component. Introducing sub-components would add organisational overhead without meaningful reuse benefit. The heading, subheading, and CTA are rendered inline using Sitecore field primitives.

**Sitecore field primitives** — use the SDK's field rendering components (or equivalent) for the heading text, subheading text, image, and link fields. This ensures Sitecore Experience Editor compatibility and proper field-level editing.

**Full-width breakout pattern** — the hero banner must break out of the parent content container to span the full viewport width. This is a CSS layout concern (e.g. negative margins with `100vw` width, or a `position`-based approach) that should be resolved during Implementation Planning. The design intent is that the hero spans edge-to-edge regardless of the container width applied by the page layout.

## Responsive Behaviour

### Mobile (below the design system's mobile breakpoint)

- The hero banner remains full-width and fixed-height (`60vh`). The height does not change on mobile — it should remain a prominent visual element.
- The heading text scales down to a smaller size appropriate for mobile readability (e.g. the lower end of the H1 range, around 28–32px or the design system's responsive heading scale).
- The subheading text remains at body size or slightly smaller, staying readable on narrow screens.
- The CTA button remains centred and at a comfortable tap target size (minimum 44×44px touch target).
- The text content region remains horizontally and vertically centred.
- No horizontal overflow occurs — text wraps naturally within the viewport width with horizontal padding from the design system's spacing scale.
- The background image continues to fill the banner area with `object-fit: cover`, cropping as needed.

### Tablet (between mobile and desktop breakpoints)

- Layout behaviour follows the same pattern as mobile — full-width, centred content, responsive text sizing.
- The heading may render at an intermediate size between the mobile and desktop scales.
- Additional horizontal padding may be present compared to mobile, following the design system's container padding at this breakpoint.
- No layout structure change occurs at this breakpoint — the hero is the same compositional design at all viewports.

### Desktop (at or above the desktop breakpoint)

- Full-width and `60vh` height as designed.
- Heading at the full H1 scale (36–48px).
- Subheading at the full body/large body scale.
- Text content region centred within the banner. Content width should be constrained (e.g. by a max-width or the design system's container width) to prevent text lines from stretching excessively on very wide viewports.
- CTA button at standard size.

### Cross-Breakpoint Rules

- The hero banner must never cause horizontal scrolling at any viewport width.
- The layered structure (image → scrim → text) remains consistent at all breakpoints.
- Text must remain readable at all breakpoints — the scrim ensures contrast, and responsive font sizing ensures the text fits without overflow or truncation.
- The CTA, when present, must remain centred and visible at all breakpoints.

## Accessibility Considerations

**Heading structure.** The heading is rendered as an `<h1>`. Pages that include the hero banner should treat this as the page's primary heading. No other `<h1>` should appear on the same page. Subsequent content sections should begin at `<h2>`.

**Subheading element.** The subheading uses a `<p>` element, preserving the heading hierarchy. This avoids introducing an `<h2>` inside the hero that would compete with the section headings in the main content below.

**Background image alt text.** The image's `alt` attribute is sourced directly from the Sitecore Image field. Authors can provide meaningful alt text (for images that convey information) or leave it empty (for purely decorative backgrounds, producing `alt=""`). The component does not override or fabricate alt text — author control is respected.

**Colour contrast.** The semi-transparent dark scrim is the primary mechanism for ensuring WCAG AA contrast (4.5:1 for normal text, 3:1 for large text) between the white/light text and the background image. The minimum enforced overlay opacity of 30% and the default of 40–50% are designed to maintain sufficient contrast for the majority of photographic backgrounds. The heading, rendered at the H1 scale, qualifies as large text (3:1 ratio required). The subheading and CTA text must meet the 4.5:1 ratio.

**Keyboard accessibility.** The CTA link is the only interactive element within the hero banner. It must be keyboard-focusable via Tab and activatable via Enter. No other element within the hero requires keyboard interaction.

**Visible focus state.** The CTA link must display a clearly visible focus indicator when focused. The focus ring must be visible against the dark scrim background — a light-coloured focus ring or a high-contrast outline is required. The design system's standard focus style should be used if it provides sufficient contrast against dark backgrounds; otherwise, an inverted or light-on-dark variant should be applied.

**No auto-play or motion.** The hero banner is a static element — no animation, auto-scrolling, or motion is present. This satisfies WCAG 2.3.1 (no flashing) and avoids motion-sensitivity concerns.

**Landmark and ARIA.** The hero banner does not require a landmark role or ARIA region. It is a content component within the `<main>` content area, not a navigational or complementary region. No additional ARIA attributes are needed beyond the semantic HTML elements (`<h1>`, `<p>`, `<a>`, `<img>`).

## Risks

**Full-width breakout styling.** The hero banner must break out of the parent content container to span the full viewport width. The breakout technique (negative margins, `100vw`, or viewport-relative positioning) may interact unpredictably with the existing page layout structure established by T001. Implementation Planning must confirm the breakout approach and verify it does not introduce horizontal overflow or layout shifts in the parent container.

**Next.js Image component constraints.** The Next.js Image component has specific requirements around dimensions and layout modes that may not align cleanly with the full-width, fixed-height, `object-fit: cover` requirement. A CSS `background-image` fallback or an unoptimised image approach may be necessary. The trade-off between image optimisation and layout flexibility should be resolved during Implementation Planning.

**Low overlay opacity accessibility.** Even with a minimum enforced opacity of 30%, certain very light or high-contrast background images may produce insufficient text contrast. The CMS Configuration Guide should advise authors to choose background images with moderate visual complexity and to preview the hero at the chosen opacity. Programmatic contrast checking is out of scope.

**`60vh` height on short viewports.** On very short viewports (e.g. landscape mobile), `60vh` may be too small to comfortably contain the heading, subheading, and CTA without text overflow. A `min-height` value may be needed as a safety measure. Implementation Planning should confirm the minimum height approach.

**Single `<h1>` constraint.** The hero banner renders an `<h1>`. If authors place the hero banner on a page that already has an `<h1>` from another component, the page will have duplicate `<h1>` elements, which is a heading hierarchy violation. This is an authoring concern rather than a component defect, but the CMS Configuration Guide should note this constraint.

## Open Questions

1. **Hero banner height token.** Should the `60vh` fixed height be defined as a design-system token or remain a component-level constant? If a token is preferred, it should be added to the design system before implementation begins.

2. **Overlay opacity field type.** Should the overlay opacity Sitecore field be a Droplink (offering preset values like 30%, 40%, 50%, 60%, 70%, 80%) or a Number field (offering free-form numeric input)? A Droplink with preset values is the safer design choice for preventing invalid input, but requires a supporting Sitecore folder of option items. Implementation Planning should confirm the field type.

3. **Full-width breakout technique.** The CSS approach for breaking the hero out of the parent container must be confirmed during Implementation Planning. The design assumes edge-to-edge rendering is achievable without horizontal overflow. If the existing page layout prevents a clean breakout, the hero's width behaviour may need to be adjusted.

4. **CTA button visual style.** The design recommends a light/white button or bordered button style against the dark scrim. The exact button style (solid fill vs. outline, colour token choice) should be confirmed during Implementation Planning to ensure it aligns with the design system's button pattern and provides sufficient contrast.
