## Title

Site Header, Header Partial Design, and Default Page Design

---

## Feature Overview

This task establishes the foundational page composition infrastructure for the site and
delivers the first visible piece of shared page chrome.

Three closely coupled design deliverables are produced together:

- A **Header Partial Design** that composes the site header into every page and exposes
  the `headless-main` and `headless-footer` placeholders for page-specific content.
- A **Default Page Design** that assembles the Header Partial Design into a complete
  page shell and becomes the site-wide default.
- The **Site Header rendering** — a horizontal header band containing an authored logo
  and Sitecore-driven primary navigation, with responsive mobile behaviour.

All subsequent page features (hero, rich text, footer, etc.) will slot into the
`headless-main` and `headless-footer` placeholders exposed by this design, making this
the design foundation for the entire site.

---

## Design Intent

- **Consistency first.** The header must look and behave identically on every page of
  the site. This is achieved structurally through the SXA Partial Design and Default
  Page Design, not through per-page duplication.
- **Content-driven.** The logo and navigation links are authored in Sitecore and
  delivered through route/layout data. The visual design must feel coherent whether
  the navigation contains two items or eight.
- **Minimal and calm.** The header should follow the design system's principle of visual
  restraint. The site logo and navigation should be clearly readable without competing
  with page content.
- **Mobile-first.** The header collapses to a hamburger menu on narrow viewports. The
  collapsed state should be as clean and accessible as the expanded desktop state.
- **Accessibility by design.** Semantic structure, visible focus, keyboard operability,
  and appropriate ARIA labelling are expected from the first implementation, not
  retrofitted afterward.

## Page / Feature Structure

### SXA Composition Model

The SXA Page Design and Partial Design define how pages are assembled in Sitecore.
From a design perspective, the composition model produces this top-level page layout
for every page using the Default Page Design:

```
┌─────────────────────────────────────────┐
│  Site Header (Header Partial Design)    │
├─────────────────────────────────────────┤
│  headless-main placeholder              │  ← page-specific content renders here
│  (populated by individual page routes)  │
├─────────────────────────────────────────┤
│  headless-footer placeholder            │  ← reserved for B003 footer (empty now)
└─────────────────────────────────────────┘
```

The Site Header occupies a persistent top band on every page. Page-specific content
(hero, rich text, etc.) is composed into `headless-main`. The footer placeholder is
wired but empty for this task.

### Site Header Structure

The Site Header rendering is a full-width horizontal band at the top of the viewport.
Its internal structure at the design level is:

```
┌─────────────────────────────────────────────────────────────────┐
│  [ Logo + link to home ]     [ Nav Link ] [ Nav Link ] [ ... ]  │  ← Desktop
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│  [ Logo + link to home ]                     [ ☰ Menu Button ]  │  ← Mobile (collapsed)
└─────────────────────────────────────────────────────────────────┘
┌─────────────────────────────────────────────────────────────────┐
│  [ Logo + link to home ]                     [ ✕ Close Button ] │  ← Mobile (expanded)
│  [ Nav Link ]                                                   │
│  [ Nav Link ]                                                   │
│  [ ... ]                                                        │
└─────────────────────────────────────────────────────────────────┘
```

Two primary sub-regions:

1. **Logo region** — left-aligned (or start-aligned in LTR), contains the authored
   logo image wrapped in a home-page link.
2. **Navigation region** — right-aligned on desktop, collapses behind a hamburger
   toggle on mobile/tablet.

## Section Breakdown

### Logo Region

**Purpose:** Brand identity and home-page anchor.

**Expected content:**
- A Sitecore-authored image (the site logo) delivered via an Image field on the header
  data source item.
- The image is wrapped in an anchor that links to the site home page (the root route,
  `/`).
- The Image field must supply an `alt` attribute for the logo; the `alt` value should
  describe the brand (e.g., the site name), not be empty.

**Visual guidance:**
- The logo should be sized to fit comfortably within the header height without
  overflowing.
- Use standard spacing from the design system (e.g., 16–24px inset on the left edge).
- The logo link should not be underlined; it is purely a visual identity element and
  navigation anchor.

**Interaction:**
- Logo link navigates to the home page on click or keyboard Enter.
- Visible focus state on the logo link follows design system focus styling.

---

### Navigation Region — Desktop

**Purpose:** Primary site navigation displayed horizontally at desktop viewports.

**Expected content:**
- A horizontal list of navigation links whose labels and URLs are sourced from Sitecore
  route/layout data.
- Each navigation item consists of a display label and a target URL derived from the
  Sitecore content tree.
- The navigation is flat (single-level); no dropdown or mega-menu is included.

**Visual guidance:**
- Navigation links are displayed in a horizontal row, right-aligned (or end-aligned)
  within the header.
- Links use the design system's primary navigation text style.
- Hover state: a subtle visual change (colour shift or underline) consistent with the
  design system's interaction model.
- Active/current page link: a visual indicator (e.g., primary accent colour or
  underline) to communicate current location. The active link should be determined by
  the current route.

**Interaction:**
- Each link navigates to the corresponding Sitecore-authored page.
- Keyboard Tab moves focus through each link in DOM order.
- Enter activates the focused link.

---

### Navigation Region — Mobile / Tablet (Collapsed State)

**Purpose:** Compact navigation entry point at narrow viewports.

**Expected content:**
- The horizontal navigation links are hidden.
- A hamburger menu button (☰) is visible at the right end of the header bar.

**Visual guidance:**
- The hamburger button uses an icon (three horizontal lines) with a visible tap target
  of at least 44×44px (meeting WCAG 2.5.5).
- The button uses the design system's primary text or icon colour; no decorative
  background unless hover/focus state.
- The button has a visible focus ring.

**Interaction:**
- Clicking or activating the button opens the navigation drawer (see expanded state).
- The button ARIA label reads "Open navigation" in the collapsed state.

---

### Navigation Region — Mobile / Tablet (Expanded State)

**Purpose:** Full navigation access at narrow viewports.

**Expected content:**
- The navigation links are visible in a stacked vertical list below the header bar,
  or overlaid as a drawer on top of the page content.
- The hamburger button icon changes to a close icon (✕) or the ARIA label changes to
  "Close navigation".

**Visual guidance:**
- The expanded navigation list should feel visually connected to the header (e.g.,
  same background colour, no visible gap between header bar and nav list).
- Navigation links are stacked vertically with consistent spacing from the design
  system (e.g., `space-y-4` or `space-y-6`).
- The overall expanded panel width spans the full viewport width on mobile.
- Links use the same style as desktop navigation links for visual consistency.

**Interaction:**
- Clicking a navigation link navigates to the target page and closes the menu.
- Clicking or activating the close button (☰ → ✕) hides the navigation.
- The ARIA label on the toggle button reflects the current state ("Close navigation"
  when expanded).

## Component Recommendations

- **SiteHeader** — the top-level rendering component. Wraps the full header in a
  semantic `<header>` element. Receives logo and navigation data from Sitecore layout
  data via JSS props. Owns the mobile open/close state as local UI state.

- **SiteHeaderLogo** — sub-component (or inline region) responsible for rendering the
  Sitecore Image field with the home-page anchor wrapper. Should use the JSS
  `<JssImage>` or equivalent to render the Sitecore Image field correctly.

- **SiteHeaderNav** — sub-component responsible for rendering the navigation link list.
  Receives an array of navigation items from layout data. Renders as a `<nav>` element
  with a descriptive ARIA label (e.g., `aria-label="Primary"`). Displays horizontally
  on desktop, hidden or visible conditionally based on the mobile open state.

- **HamburgerButton** — a focusable `<button>` element that toggles the mobile
  navigation open/closed. Manages its own ARIA label based on the current open/closed
  state. This is part of the SiteHeader component rather than a standalone rendering.

These are design-level component roles. Implementation Planning will define the exact
file structure, import paths, and prop interfaces.

## Navigation Data Design

The specification identifies the shape of the Sitecore navigation data as an open
question. For design purposes, the following intent is established:

- Navigation items consist of a **display label** (text) and a **target URL**.
- The data is delivered to the Site Header rendering via Sitecore layout data (JSS
  component fields), not fetched separately at runtime.
- The simplest supported model is a **list field** on the header component's data source
  item, where each entry in the list provides a label and a link.
- A secondary supported model is that navigation items are represented as **child items
  of a navigation root item** in the Sitecore content tree, projected into the header
  component's layout data.
- Implementation Planning should confirm which model is available in the existing
  codebase and Sitecore setup. Either model produces the same rendered output from a
  design perspective: a flat list of labelled links.

## Responsive Behaviour

### Breakpoint

The transition between the desktop navigation layout and the mobile hamburger layout
should occur at the **large breakpoint** (`lg`, nominally 1024px). Below 1024px,
the hamburger pattern applies. At 1024px and above, the full horizontal navigation
is displayed.

This recommendation aligns with the design system's mobile-first approach and ensures
that tablet-sized viewports (768px–1023px) also receive the more compact mobile
navigation.

### Mobile (below 1024px)

- The header bar is a single horizontal row: logo on the left, hamburger button on the
  right.
- The navigation links are not visible until the hamburger is activated.
- When expanded, navigation links stack vertically in a panel below or overlaid on the
  page.
- Text and tap targets remain at comfortable sizes for touch interaction.
- No horizontal overflow of the header bar itself.

### Tablet (768px–1023px)

- Follows the mobile pattern (hamburger navigation).
- The header bar may have slightly more horizontal padding than on mobile, but the
  fundamental layout pattern is the same.

### Desktop (1024px and above)

- Logo is visible at the left (start) of the header bar.
- Navigation links are arranged horizontally at the right (end) of the header bar.
- The hamburger button is not visible.
- The header bar should not exceed a sensible content width; horizontal padding should
  align with the site's container pattern to prevent the header content from stretching
  to extreme widths on very large screens.

### Cross-breakpoint rules

- The header must not cause horizontal overflow at any viewport width.
- Content hierarchy must remain clear at all sizes.
- The header height should remain consistent at a given viewport size regardless of
  navigation item count within expected bounds.

## Accessibility Considerations

- **Semantic structure**: The outermost element of the Site Header rendering is
  `<header>`. Navigation links are wrapped in `<nav aria-label="Primary">`.
- **Heading hierarchy**: The header does not contain heading elements; it is a landmark
  region. Page headings begin in the `headless-main` placeholder content.
- **Focus management**: Focus order follows the natural DOM order — logo link, then
  navigation links (desktop) or hamburger button (mobile). When the mobile navigation
  opens, focus should not be trapped; users can Tab through the revealed navigation
  links naturally.
- **Keyboard operability**: All interactive elements (logo link, nav links, hamburger
  button) are reachable and activatable via keyboard. The hamburger button responds to
  Enter and Space.
- **Visible focus states**: All interactive elements must display a visible focus ring
  consistent with the design system's focus styling.
- **Contrast**: Logo alt text and navigation link text must meet WCAG AA contrast
  ratios against the header background colour.
- **ARIA labelling**: The hamburger toggle button must have an `aria-label` that reflects
  the current state: "Open navigation" (collapsed) or "Close navigation" (expanded).
  The `<nav>` element must have a descriptive ARIA label to distinguish it from other
  navigation landmarks if they exist on the page.
- **Logo alt text**: The Sitecore Image field for the logo must carry meaningful alt
  text (the site name or brand description). This is an editorial requirement reflected
  in the CMS Configuration Guide.

## Risks

- **Navigation data shape**: The exact structure of the Sitecore layout data that
  provides navigation items to the header rendering is not yet confirmed. If the data
  model requires a custom navigation rendering or a specific content template that does
  not yet exist, implementation scope may expand. This must be resolved in
  Implementation Planning.
- **Header background / colour token**: The design system defines a neutral-dominant
  palette but does not specify an exact header background colour token. Implementation
  Planning should confirm whether a token exists or whether a new, design-system-aligned
  value is needed.
- **Logo size and proportions**: The authored logo's aspect ratio is unknown. The
  implementation should constrain the logo image dimensions (max-height on the header,
  `object-fit: contain`) to handle logos of varying proportions gracefully.
- **Home page existing Page Design**: If the site's home page already has a Page Design
  assigned, replacing it with "Default" may affect existing page composition. The CMS
  Configuration Guide must address this explicitly.
- **Breakpoint confirmation**: The recommended 1024px breakpoint is a design
  recommendation. Implementation Planning should confirm this aligns with any
  breakpoint tokens or Tailwind-style config already in use in the project.
