## Title

Site Footer and Footer Partial Design

---

## Feature Overview

This feature delivers a fully authored, accessible Site Footer rendering together with the Sitecore SXA Partial Design and Page Design configuration needed to display it on every page of the site.

The footer is a persistent piece of page chrome that carries the site brand (logo linking to the home page), a secondary navigation link list, social media links for Facebook, X (Twitter), and LinkedIn, and authored copyright text. All content is sourced from a dedicated Sitecore data source item, allowing editors to update any part of the footer without a code change.

A new "Footer" Partial Design places the Site Footer rendering inside the `headless-footer` placeholder. The existing "Default" Page Design is updated to reference this Partial Design, so every page already using the Default design gains the footer automatically.

---

## Design Intent

The footer should feel like a natural, calm conclusion to every page — trustworthy and informative without competing with the authored content above it. The following design goals guide this implementation:

**Brand grounding.** The site logo in the footer reinforces brand identity and provides a clear return-to-home affordance. It should be visually prominent within the footer without overshadowing the page content above.

**Structured clarity.** The three-column desktop layout separates distinct types of content — brand identity, navigation, and social presence — into clearly distinct regions. Within each region, items should be easy to scan and read. Spacing, not decorative elements, creates the separation.

**Visual restraint.** The footer follows the design system's principle of visual restraint. It uses a neutral background tone drawn from the design system's neutral palette, light text on that background for contrast, and minimal decoration. No gradients, heavy shadows, or accent colour overuse are introduced.

**Content-first responsiveness.** On mobile, the three columns stack into a single column in a logical reading order (logo → navigation → social links) to preserve hierarchy and remain fully usable at small viewport widths.

**Accessibility by default.** Semantic HTML landmarks, visible focus states, keyboard navigability, and accessible names for all interactive elements are structural requirements, not afterthoughts. Every interactive element must be reachable and identifiable by assistive technologies.

**Design system alignment.** All typography, spacing, colour, and breakpoint choices must draw exclusively from design system tokens. No arbitrary values are introduced.

## Page / Feature Structure

The Site Footer is a full-width component rendered inside the `headless-footer` placeholder at the bottom of the page layout. It is composed of two distinct horizontal zones within a shared container:

**Main content row** — three equal or proportionally balanced columns:
- Logo column (left): site logo image, acting as a home page link
- Navigation column (centre): secondary navigation link list
- Social column (right): social media platform links

**Copyright bar** — a full-width sub-row below the main content row, containing the authored copyright text. It sits at the bottom of the footer container, visually separated from the column row by spacing rather than a border or decorative rule.

The entire footer is wrapped in a `<footer>` landmark element. Within it, the navigation link list is wrapped in a `<nav>` element. These two structural landmarks give the footer a semantically meaningful role in the page outline and expose it correctly to screen readers and browser accessibility tools.

The footer component is authored via a single Sitecore data source item. The Footer Partial Design references this data source item, allowing a single edit to propagate to every page using the Default Page Design.

## Section Breakdown

### Logo Column

**Purpose:** Brand identity and primary home navigation affordance within the footer.

**Expected content:** A single authored image (Sitecore Image field) rendered as a visible logo. The image is wrapped in an anchor element whose `href` targets the site home page.

**Visual guidance:** The logo should render at a size appropriate for a footer context — visually readable without dominating. It should be displayed using its natural proportions (no forced distortion). The logo image should have appropriate `alt` text, either authored in Sitecore's image alt field or defaulting to the site name if the alt field is empty.

**Interaction:** Clicking or activating the logo link navigates the user to the site home page. The link is a standard in-page anchor — no new tab. The link is keyboard-reachable and displays a visible focus indicator consistent with the design system's focus styling.

---

### Navigation Column

**Purpose:** Provide secondary navigation links so visitors can reach key pages from any point in the site.

**Expected content:** A variable-length list of links sourced entirely from the authored Sitecore Link List field on the data source item. The number of links, their labels, and their destinations are controlled by the author. No link text or URL is hard-coded in the component.

**Visual guidance:** Links are rendered as a vertical list of plain text links. No bullet points, icons, or decorative markers are used. Each link uses the design system's body text size and a muted-to-standard text colour that contrasts clearly against the footer background. On hover, links display a subtle visual change (underline or slight colour shift) consistent with the design system's interaction principles.

**Interaction:** Each link is a standard HTML anchor. Links open in the same tab (the author-defined link target is respected but no forced new-tab behaviour is applied by the component). The list is wrapped in a `<nav>` element with `aria-label="Footer navigation"`.

**Semantic structure:** The link list is rendered as a `<ul>` / `<li>` structure inside the `<nav>` element, giving it a meaningful list structure that screen readers can announce as a navigation list with item count.

---

### Social Column

**Purpose:** Provide direct links to the organisation's social media presence on Facebook, X (Twitter), and LinkedIn.

**Expected content:** Up to three authored links, one per platform, each sourced from an individual General Link field (Facebook, X (Twitter), LinkedIn) on the data source item. Each rendered link opens in a new browser tab (`target="_blank"`). A social link field that is empty or null must not produce a rendered anchor element — conditional rendering per field is required.

**Visual guidance:** Social links may be rendered as icon links or as icon + text links. The recommended approach is an SVG icon paired with a visually hidden or visible platform name label, so the link is identifiable visually and to assistive technologies. The icons should be a consistent size appropriate for a footer context, using the design system's spacing scale for any gap between them. The column layout aligns social links vertically (stacked) or in a compact horizontal row within their column — the choice should be consistent and predictable at all viewport widths where the three-column layout is active.

**Interaction:** Each rendered social link opens the authored URL in a new tab. `target="_blank"` is applied by the component, not the author. Each anchor carries either visible text that names the platform, or an `aria-label` attribute naming the platform (e.g. `aria-label="Facebook"`, `aria-label="X (Twitter)"`, `aria-label="LinkedIn"`). Icon-only links without an accessible name are not permitted.

**Risk note:** The availability of SVG icon assets for the three platforms must be confirmed during Implementation Planning. If appropriate icons are not available, text-only links with platform names are the required fallback — this must not be left as a deferred concern.

---

### Copyright Bar

**Purpose:** Display the authored copyright statement at the bottom of the footer.

**Expected content:** The full string from the authored Sitecore Single-Line Text field. The string is rendered as-is with no truncation, transformation, or additional content added by the component.

**Visual guidance:** The copyright text is rendered as a single line of supporting text — smaller than the body text size, muted colour, consistent with the design system's guidance for metadata and secondary text. It spans the full width of the footer container. It is visually separated from the column row above by spacing drawn from the design system's spacing scale.

**Interaction:** The copyright bar is non-interactive. No links, buttons, or focusable elements are present.

## Component Recommendations

**Footer shell** — a single `SiteFooter` component forming the `<footer>` landmark element, housing the container, the three-column row, and the copyright bar. This component receives the Sitecore layout data fields as props and owns all rendering logic.

**Logo link** — reuse the same image-with-link pattern established by the header (T001) where applicable. Renders an `<Image>` (or equivalent Sitecore-field-aware image primitive) wrapped in an `<a>` with an `href` pointing to the home page.

**Navigation link list** — a lightweight sub-component or inline rendering loop that maps the authored Link List field to a `<nav>` / `<ul>` / `<li>` / `<a>` structure. This follows the same authored-list-to-nav pattern used elsewhere in the design system's navigation component type.

**Social link item** — a small, focused sub-component or inline conditional that renders a single social anchor only when the corresponding General Link field is non-empty. It applies `target="_blank"` and the accessible name. Icon rendering is handled here if icons are available.

**Layout container** — uses the design system's standard container pattern (centred, constrained max-width, consistent horizontal padding) so the footer width and alignment matches the main page content above it.

**Three-column grid** — uses the design system's layout tokens to define the three-column desktop grid. The grid collapses to a single column at the mobile breakpoint using mobile-first layout thinking. Column order in the stacked layout is logo → navigation → social.

## Responsive Behaviour

The footer is designed mobile-first. Default layout is single-column stacked. The three-column layout activates at the design system's defined mobile/tablet breakpoint and above.

### Mobile (below the design system's mobile breakpoint)

- The three columns (logo, navigation, social) stack vertically in a single column.
- Stacking order: logo first, navigation links second, social links third. This order preserves the logical reading hierarchy.
- Each region occupies the full container width.
- Social links that were laid out horizontally on desktop may remain horizontal (as a compact row) or stack vertically within their region — either is acceptable as long as items remain comfortably tappable (minimum touch target size consistent with design system guidance).
- Copyright text spans full width below the stacked columns.
- Text sizes remain at body and supporting text sizes from the design system — no font scaling is applied specifically for mobile.
- Vertical spacing between stacked regions should use a value from the design system's spacing scale (minimum `space-y-6` / 24px equivalent between regions).
- The footer must not overflow horizontally at any mobile viewport width. All content must remain within the container bounds.

### Tablet (at or above the mobile breakpoint, below the desktop breakpoint)

- The three-column layout activates at the mobile breakpoint. At tablet widths, the three columns are visible and functional.
- Column proportions may be equal thirds or weighted (e.g. logo column narrower, nav column wider) — the exact proportions are a judgment call for Implementation Planning, but should use the design system's grid or flexbox pattern consistently.
- Container horizontal padding should remain consistent with the rest of the page layout at this breakpoint.
- No additional layout changes are needed between the mobile breakpoint and the desktop breakpoint beyond any natural scaling of the container width.

### Desktop (at or above the desktop breakpoint)

- Three columns are fully visible: logo (left), navigation (centre), social (right).
- The container respects the design system's maximum content width to prevent the footer from becoming excessively wide on large viewports.
- Column spacing uses design system spacing tokens (`gap` values from the spacing scale).
- Copyright text sits in the full-width bar below the three-column row.
- No horizontal overflow occurs.

### Cross-Breakpoint Rules

- Column stacking order on mobile must exactly match top-to-bottom reading order: logo → navigation → social.
- The footer must never cause horizontal scroll at any breakpoint.
- Content hierarchy must remain clear at every breakpoint — the logo is always visually distinct, the navigation list is always scannable, and the social links are always identifiable.
- The copyright bar always appears below the column content at all breakpoints.

## Accessibility Considerations

**Semantic landmarks.** The outermost element of the Site Footer rendering must be a `<footer>` HTML landmark element. This exposes the footer as a `contentinfo` landmark to assistive technologies, allowing screen reader users to navigate directly to it. The secondary navigation block must be wrapped in a `<nav>` element with `aria-label="Footer navigation"` to distinguish it from the primary site navigation (which also uses a `<nav>` landmark).

**Heading hierarchy.** The footer does not introduce any headings. Visual groupings (logo, navigation, social links) are structured using semantic HTML elements (`<nav>`, `<ul>`) and ARIA labels rather than heading elements. This avoids disrupting the page heading outline.

**Keyboard navigation.** All interactive elements — the logo link, each navigation link, and each social link — must be reachable by sequential Tab key navigation. The tab order should follow a logical reading order: logo link first, navigation links in the authored list order, social links in the fixed platform order (Facebook → X (Twitter) → LinkedIn). No interactive element may be skipped or unreachable from keyboard focus.

**Visible focus indicators.** Every focusable element in the footer must display a visible focus indicator when focused by keyboard. The indicator must meet the design system's defined focus style (consistent with focus indicators used elsewhere in the application). No element may have its native focus outline suppressed without an equivalent visible replacement.

**Social link accessible names.** Each social link must carry an accessible name that identifies its destination platform. If rendered as icon-only links, each anchor must include an `aria-label` naming the platform (e.g. `aria-label="Visit us on Facebook"`). Alternatively, visible text labels may be included alongside or below the icon. Icon-only links without either an `aria-label` or visually-hidden text are not acceptable and do not satisfy the accessibility requirement.

**Empty social link fields.** If an author leaves a social link field empty, the component must render no anchor element for that platform. An empty `<a>` element or a broken link is not permitted.

**Alt text for the logo.** The logo image element must have meaningful `alt` text. The component should use any alt text value authored in the Sitecore Image field. If the alt value is empty, the component should default to the site name or a descriptive fallback (e.g. `"Site logo"`) rather than leaving the `alt` attribute empty on a linked image, which would expose the image URL to screen readers.

**Navigation link list structure.** The navigation links inside `<nav>` must be rendered as a `<ul>` / `<li>` list. This gives the list meaningful structure that screen readers can announce as a navigation list with a count of items, which aids orientation for screen reader users.

**Colour contrast.** All text in the footer — navigation links, social link labels or icons, and copyright text — must meet the WCAG AA minimum contrast ratio (4.5:1 for normal text, 3:1 for large text) against the footer background colour. The design system's neutral palette is used for the footer background, and text colour tokens must be chosen to satisfy contrast requirements without exception.

**Social link new-tab behaviour.** Links that open in a new tab should signal this to users where possible. If the design uses icon-only social links with `aria-label`, consider appending `"(opens in new tab)"` to the label or providing a visually hidden text equivalent so screen reader users are informed of the behaviour before activating the link.

## Risks

**Default Page Design impact.** Adding the Footer Partial Design to the Default Page Design will introduce a footer region on every page currently using that design. Any page that previously had no footer will gain one when this change is applied. The visual impact on existing authored pages must be verified during QA.

**Placeholder key mismatch.** The `headless-footer` key used in the Sitecore Footer Partial Design configuration must exactly match the key registered in the head application's placeholder configuration. A mismatch will silently prevent the footer rendering from appearing. This must be verified during Implementation Planning and confirmed as part of the CMS Configuration validation steps.

**SVG icon asset availability.** The recommended design uses SVG icons for the social links. If appropriate assets are not available in the project, the implementation must fall back to text-only links. This risk must be resolved before the Build stage begins. An unresolved icon strategy will produce an inconsistent or inaccessible result.

**Social link accessible name implementation.** If icon-only social links are used, the accessible name strategy (`aria-label` on the anchor, or visually hidden text inside the anchor) must be chosen and consistently implemented. Inconsistent or missing accessible names will cause the component to fail AC-05 and AC-10. This design prescribes `aria-label` as the primary approach; Implementation Planning should confirm the chosen pattern.

**Route/layout data shape for the Link List field.** The exact shape of the Sitecore layout data for the Link List field as it arrives in the head application must be confirmed. If the serialisation format differs from the standard JSS field conventions or from the approach used for navigation links in the Site Header (T001), a data transformation layer may be required. This must be resolved during Implementation Planning.

**Column proportion and alignment on tablet.** The three-column layout is specified at a design intent level but the exact proportional split is not prescribed. An unresolved proportion choice may produce an unbalanced layout where, for example, the logo column is too wide or the navigation column is too narrow on certain viewport widths. Implementation Planning should confirm the column widths.
