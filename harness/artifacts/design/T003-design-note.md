## Title

Automated CI/CD Testing — Workflow Design

---

## Feature Overview

This feature introduces a GitHub Actions workflow that validates the head application's code quality on every pull request. It runs the existing Jest test suite, ESLint linter, and TypeScript type checker, providing immediate automated feedback before code review.

---

## Design Intent

- **Simplicity**: A single workflow file with a single job and sequential steps. No matrix builds, no multi-job orchestration.
- **Speed**: Leverage dependency caching to minimize install time on repeated runs.
- **Clarity**: Each validation step (test, lint, type-check) runs as a distinct named step so that failures are immediately identifiable in the GitHub Actions UI.
- **Correctness**: All commands are scoped to the head application's subdirectory to avoid operating on unrelated project areas.
- **Extensibility**: The workflow structure should allow future additions (e.g., additional jobs for other head applications or test types) without reworking the existing configuration.

## Workflow Structure

The CI workflow is organized as a single YAML file with one job containing sequential steps:

### Workflow File

- Location: `.github/workflows/ci.yml`
- Trigger: `pull_request` events (`opened`, `synchronize`, `reopened`) targeting the default branch

### Job: Validate

A single job named `validate` (or similar) running on `ubuntu-latest`:

1. **Checkout** — Check out the repository source code.
2. **Setup Node.js** — Configure the correct Node.js version with npm caching enabled.
3. **Install Dependencies** — Run `npm ci` in the head application directory for reproducible installs.
4. **Run Tests** — Execute the Jest test suite.
5. **Run Lint** — Execute ESLint.
6. **Run Type Check** — Execute the TypeScript compiler in `--noEmit` mode.

All steps after checkout use the working directory `src/headapps/rob-harness-engineering/`.

### Design Rationale — Single Job

A single job with sequential steps is appropriate because:
- All three checks share the same dependencies and setup.
- Avoiding parallel jobs reduces GitHub Actions minute consumption.
- A single job avoids redundant checkout and install steps.
- The sequential approach keeps the workflow simple and easy to debug.

## Section Breakdown

### Trigger Configuration

The workflow triggers only on pull request events targeting the default branch. Push events to the main branch are out of scope. The trigger types (`opened`, `synchronize`, `reopened`) cover the standard pull request lifecycle.

### Caching Strategy

Dependency caching uses the built-in cache option of `actions/setup-node` with `cache: 'npm'`. This caches the npm global cache directory. The `package-lock.json` in the head application directory serves as the cache key, so the cache invalidates when dependencies change.

### Working Directory Scoping

All npm commands use a `working-directory` setting pointing to `src/headapps/rob-harness-engineering/`. This ensures commands operate on the correct `package.json` and `node_modules`.

### Failure Behavior

Each step runs in sequence. If any step fails, the job stops and reports failure. GitHub Actions natively surfaces which step failed, providing actionable feedback.

### Branch Protection Documentation

A documentation section (in the workflow file comments or a separate markdown section in the PR) will describe how to:
- Navigate to the repository's branch protection settings.
- Add the workflow job as a required status check.
- Enable "Require status checks to pass before merging."

## Dependencies

- GitHub Actions runner environment (`ubuntu-latest`) with Node.js support.
- `actions/checkout` action for repository checkout.
- `actions/setup-node` action for Node.js setup and npm caching.
- Existing npm scripts in the head application's `package.json` for test, lint, and type-check.

## Risks

- If the head application's `package-lock.json` is missing or out of sync, `npm ci` will fail. This should be verified during Implementation Planning.
- GitHub-hosted runner environment differences from local development could surface latent test issues.
