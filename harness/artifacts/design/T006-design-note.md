## Title

Teaser Component

---

## Feature Overview

The Teaser Component is a reusable, author-placed rendering for the `headless-main` placeholder. It combines an optional image, optional editorial text fields (pretitle, title, description), an optional primary destination link, and zero or more labeled call-to-action links. Seven distinct presentation variants allow a single component to serve featured articles, recent articles, adventures, card grids, compact list items, carousel slides, and restricted-access content — all through author-controlled field values and a variant selection.

The component supports sourcing its title, description, and image either from directly authored field values or from a linked content item, giving authors control over whether a teaser presents standalone copy or inherits identity from the content it promotes.

---

## Design Intent

The overarching design objective is a single composable editorial block that remains coherent across radically different visual treatments while exposing only one content model to authors.

**Hierarchy preservation**: regardless of variant, the content reads in the order image → pretitle → title → description → actions. Variants may reposition these regions spatially (side by side, overlaid, constrained), but the editorial priority does not change.

**Content-first restraint**: the design should follow the project design system's visual restraint principle. Spacing, neutral tones, and typography drive distinction between variants rather than heavy borders, gradients, or decorative chrome. The serif title treatment, bold pretitle, generous line spacing for descriptions, and filled uppercase CTA treatment reflect the existing WKND/design-system aesthetic.

**Variant coherence**: each variant is a different visual expression of the same content anatomy. Implementation should share as much structural logic as possible, varying only the layout geometry, spacing, and image treatment per variant.

**No hover-only state**: every destination, restriction state, and interactive affordance must be visible via keyboard focus and accessible metadata, not only through hover effects.

**Accessible by default**: heading levels are configurable within an allowed range, images carry alt text or are decorative, CTAs have meaningful labels, and the secure variant communicates restriction in text as well as visually.

## Page / Feature Structure

The Teaser Component is not a page-level layout — it is a rendering composed into the `headless-main` placeholder by a content author alongside other authored components. Its internal structure is fixed regardless of which variant is selected:

```
Teaser
  ├── Image Region (optional)
  │     image, alt text or decorative state, optional focal positioning
  └── Content Region
        ├── Pretitle (optional)
        ├── Title (optional, configurable heading level)
        ├── Description / rich text (optional)
        └── Action Area
              ├── Primary link (optional, makes teaser a linked unit)
              └── CTA links (0..n, each with label and destination)
```

The variant determines how Image Region and Content Region are arranged spatially and how image height, content width, typography scale, and overlay behavior are applied. The anatomy itself does not change.

When the teaser has no image, text, or action content, it produces the delivery environment's standard empty-component state and renders no meaningful output in the published route.

## Section Breakdown

### Image Region

**Purpose**: provides the primary visual anchor for the teaser.

**Expected content**: a single image with author-provided alternative text (or a decorative flag when the image is purely presentational). Authors may also configure focal positioning — `imagetop` or `imagebottom` — to direct the crop toward the subject when the image is displayed at a constrained height.

**Visual guidance**: the image must preserve its subject through responsive cropping. It should not be distorted or stretched. In variants that constrain image height (card, list), the focal positioning setting determines which portion of the image remains visible.

**Interaction**: if a primary link is configured and the variant does not use separate actions, the image region should be included within the linked region so the entire teaser is navigable. If separate actions are present, the image must not be a separate interactive element that creates ambiguous nested navigation.

---

### Pretitle

**Purpose**: a short contextual label that frames the teaser subject before the title is read.

**Expected content**: a brief phrase authored directly (e.g., a category, section name, or date context). This field is not sourced from a linked content item.

**Visual guidance**: displayed in a visually distinct treatment — bold, smaller text — above the title. In the `card` variant, the pretitle appears as a contrasting badge positioned at the top-right of the image rather than inline with the content stack.

---

### Title

**Purpose**: the primary editorial heading for the teaser.

**Expected content**: authored directly or resolved from the linked content item when title sourcing is enabled. The heading level is configurable by the author within the design system's allowed range (H2–H4).

**Visual guidance**: the title should be the most visually prominent text element in the content region. The design system's serif heading treatment applies at the scale appropriate to the selected heading level. In `list` variant, the title uses a sans-serif bold uppercase treatment at a smaller scale. In `card` variant, the title is suppressed in favor of the pretitle badge and action.

**Interaction**: when the teaser uses a primary link and no separate actions, the title may be part of the linked region. It must have a meaningful accessible name without relying on surrounding visual context.

---

### Description

**Purpose**: supporting rich-text copy that elaborates on the teaser's subject.

**Expected content**: authored directly or resolved from the linked content item when description sourcing is enabled. Rendered as sanitized rich text.

**Visual guidance**: body-scale text with generous line spacing following design system body text guidance (16–18px, generous line height, limited line length for readability). The description should support the title rather than compete with it.

**Layout note**: in `card` variant, the description is suppressed. In `list` variant, description may appear as a small supporting line in a muted tone.

---

### Action Area

**Purpose**: exposes the teaser's destination(s) as explicit interactive elements.

**Expected content**: zero or more labeled CTA links, each with its own visible label and destination URL. An optional primary link that makes the broader teaser region navigable.

**Visual guidance**: CTAs use the design system's filled uppercase button treatment. On `card` variant, the action is bottom-aligned. On `secure` variant, actions use a subdued treatment visually consistent with the muted presentation. Each CTA must remain visually and interactively distinct from other CTAs and from the primary linked region.

**Interaction rules**:
- If a primary link is configured and no separate CTAs are present, the linked region encompasses the teaser block.
- If separate CTAs are present, the primary link must not wrap the CTAs — each CTA remains independently activatable.
- Multiple CTAs must each have distinct focus states and must not intercept each other's activation.

## Variant-Specific Design Guidance

### `default`

Standard stacked or side-by-side layout. Image and content presented at equal visual weight. No overlay. Suitable for general editorial placement in the main content area.

### `featured`

A prominent split composition intended to anchor a page section. The image occupies the larger region (roughly two-thirds of the horizontal space on desktop); the content pane is narrower and uses a contrasting light-gray background. On small screens the split collapses into a vertical image-above-content stack. The content pane should have adequate internal padding so text does not feel cramped against the image boundary.

### `hero`

A large-format image stage for high-impact placement. On desktop, a white content panel overlaps the lower portion of the image (creating an overlay/overlap visual). On small screens, the image and content stack vertically with the image above the copy and the overlay panel becomes normal block content below the image. The image stage is substantially taller on desktop than on mobile. Content inside the panel uses the full serif heading treatment at a larger heading scale.

### `card`

A compact, image-forward block designed for use inside grids. Fixed square-like proportions with the image filling most of the block height. The image is clipped to the fixed dimensions. Title and description are suppressed; the primary content elements are the pretitle badge (top-right overlay, contrasting background) and a bottom-aligned CTA. Hover may apply a subtle zoom to the image and a change to the action treatment, but these are supplementary — the destination must be discoverable via focus and touch without hover.

### `list`

A compact horizontal editorial item: constrained-height image on one side, bold uppercase sans-serif title and smaller gray uppercase supporting text on the other. Suitable for recent-articles or related-content lists. The image height is smaller than in other variants. Typography is purposefully compact and scannable.

### `slide`

A tall, full-bleed image composition intended for placement inside a carousel container. Content (pretitle, title, description, actions) is positioned toward the lower-left of the image on large screens; on small screens, content stacks below the image centered within the column. The title is large-scale serif. Supporting copy is constrained to a readable column width so it does not span the full image width. The teaser itself is responsible only for its internal content and layout; the carousel container manages transition behavior.

### `secure`

A visually muted version of the default or featured layout, communicating that the associated content is restricted. The teaser is de-emphasized using reduced contrast or opacity on the image and content areas. A restriction cue (icon + visible text label) appears near the upper-left of the component. The CTA uses a subdued treatment. The restriction cue must convey the state in accessible text or metadata, not by icon alone. The teaser does not enforce or verify access — it only signals the state provided by the content/delivery system.

## Component Recommendations

The following UI roles and patterns should be used. These are design-level recommendations — implementation details are for the Tech Lead stage.

- **Responsive image primitive**: handles alternative text, decorative state, and focal positioning (top/bottom crop intent). Should support responsive delivery without stretching or distorting the image subject.
- **Heading level adapter**: renders the heading at the author-selected level (H2–H4) without hard-coding a specific element. Used for the title field.
- **Rich-text block**: renders sanitized rich text for the description field. Should constrain output to readable line lengths and not introduce uncontrolled markup.
- **Link/anchor wrapper**: used for both the primary link (wrapping the teaser region) and individual CTA links. Must support an accessible name derived from the title or an explicitly authored label.
- **CTA button/link element**: applies the design system's filled uppercase action treatment. Used for the labeled call-to-action links in the action area.
- **Pretitle text element**: a small, bold, muted-color label. In `card` variant, this becomes a badge overlay element positioned at the top-right of the image.
- **Restriction cue element** (secure variant): an icon + text pair that communicates the restriction state accessibly.

All of these should be lightweight and follow the design system's preference for simple, composable components over large complex UI libraries.

## Responsive Behaviour

### Mobile (< ~768px)

- All variants stack vertically: image above content.
- `featured`: split collapses to vertical stack; content pane becomes full-width block below the image.
- `hero`: overlay panel moves to normal document flow below the image; image height reduces to a mobile-appropriate proportion (shorter than desktop stage).
- `slide`: content moves below the image, centered within the column.
- `card` and `list`: remain compact; maintain readable line lengths within a narrow single column.
- `secure`: stacked like `default`; restriction cue and subdued treatment remain legible at mobile widths.
- All linked regions and CTA targets must maintain usable touch targets (minimum 44×44px effective area).
- Focus rings and pressed states must be visible at all mobile breakpoints.

### Tablet (~768px–1024px)

- `featured`: the split layout may begin appearing at tablet widths, or may remain stacked depending on the available column width. The design should avoid awkward intermediate states; a clean breakpoint at which the split engages is preferable.
- `hero` and `slide`: image height scales up from mobile but is not yet at full desktop proportions.
- `card` and `list`: may appear in multi-column grid contexts depending on the surrounding layout composition.
- Typography scales from mobile to tablet should remain within the design system heading scale without abrupt jumps.

### Desktop (> ~1024px)

- `featured`: full split composition (large image region + narrower content pane).
- `hero`: full image stage height; white content panel overlapping lower portion of image.
- `slide`: tall image-backed composition; content positioned lower-left; supporting copy in a constrained readable column.
- `card` and `list`: appear comfortably in multi-column grid layouts.
- `default` and `secure`: presented at full intended proportions.

### Cross-breakpoint rules

- No variant should cause horizontal overflow at any supported viewport width.
- Content hierarchy (image, pretitle, title, description, actions) must be preserved at all breakpoints — no content may be hidden behind the image or clipped by the viewport edge.
- Hover styling is supplementary at all breakpoints; all states must also be available via keyboard focus and touch.

## Accessibility Considerations

**Heading hierarchy**: the title uses a heading element at the author-selected level (H2–H4). Authors must be guided to choose a level appropriate to the surrounding page structure. The heading must not be skipped relative to the surrounding page hierarchy. This is an authoring governance concern; the component must render whatever level is configured without artificially restricting to H2 if the page context requires H3.

**Image alternative text**: every non-decorative image must carry a non-empty `alt` attribute authored specifically for the teaser context. Images marked as decorative must be hidden from the accessibility tree (empty `alt` and `role="presentation"` or equivalent). The authoring experience must make the alt text and decorative flag clearly available.

**Link and action labels**: primary link accessible name should derive from the title where the title is the primary teaser label. If a title is not present, an explicit accessible name must be authored. CTA labels must describe the destination or action without relying on color or surrounding context.

**No ambiguous nested interactivity**: a teaser using a primary link and separate CTAs must not create a situation where a screen reader or keyboard user cannot distinguish the primary teaser link from individual actions. The primary link must not wrap the CTA elements. Each interactive element must be independently reachable and activatable.

**Focus-visible treatment**: every interactive element (primary link, each CTA) must display a visible focus ring using the design system's focus treatment. Focus must not disappear when an overlay or image-forward layout clips the content region. Overlay-positioned elements (hero, slide, card badge) must ensure their focus states are rendered above the image layer.

**Secure variant restriction cue**: the restriction cue must combine a visual indicator (icon) with visible text (e.g., "Members only" or "Restricted") or an accessible ARIA label. The teaser must communicate that content access is controlled without implying that the teaser itself makes the access decision.

**Rich-text description**: rendered output must preserve semantic structure (paragraphs, inline emphasis). It must not introduce layout-breaking elements, uncontrolled nesting, or color-only distinctions.

**Touch targets**: at mobile breakpoints, all linked regions and CTA buttons must meet minimum touch target guidance (44×44px effective area or equivalent).

## Risks

**Overlay focus ring visibility**: the `hero`, `slide`, and `card` variants layer content over images. If focus rings are clipped by the image container's `overflow: hidden` or rendered below the image stacking context, keyboard users will lose focus visibility. The design must ensure all interactive elements within overlay regions render focus states above the image layer.

**Nested navigation in multi-action teasers**: when a primary link and multiple CTAs coexist, the primary link wrapping strategy must be carefully designed to avoid wrapping the CTA elements. This is the highest-risk interaction pattern across all variants and must be a first-class concern in the implementation plan.

**Secure variant cue legibility across all variants**: the restriction cue is defined for the secure variant, but the secure variant may itself use a featured, hero, card, or other layout geometry. The cue placement (upper-left) must remain legible across all potential base layouts. This may require variant-specific cue positioning adjustments.

**Card variant: description and title suppression**: the card variant suppresses description and, in the strong form, the title. If an author has authored content in those fields and then switches to `card` variant, the content is not rendered but remains in the CMS. The authoring experience should make this behavior clear so authors understand that switching variants affects what is visible.

**Slide variant carousel contract ambiguity**: the spec notes that the slide variant is for use inside a carousel container. The design note does not define the carousel container. If the carousel container introduces layout constraints (fixed height, overflow, transition clipping) that conflict with the slide variant's layout intent, those conflicts will need to be resolved at implementation or carousel-design time.

## Open Questions

1. **Maximum CTA count**: is there a practical upper bound on the number of call-to-action links per teaser for layout coherence? Without a limit, very long action lists could break the intended compact action area, especially in `card`, `list`, and `slide` variants. A recommended upper bound of 2–3 actions should be confirmed.

2. **Image sourcing fallback**: when image sourcing is enabled and neither the linked content item nor the current content item has an image, should the image region be omitted entirely (treating it as if no image was authored), or should a placeholder/empty state be rendered? The expected behavior should be confirmed to align the component's partial-content handling.

3. **Heading level range**: the design system heading scale runs H1–H4. Should the Teaser title be constrained to H2–H4 (excluding H1, which is typically a page-level title), or is the full H1–H6 range permissible? Confirming the allowed range prevents misuse that would break surrounding page heading hierarchy.

4. **Slide variant and carousel integration**: does the carousel container that hosts `slide` teasers define any integration contract the teaser must participate in (e.g., active/inactive visibility signals, aria-hidden toggling during transitions)? If so, those contracts should be identified before the Tech Lead designs the teaser's slide implementation so the design is compatible with the eventual carousel.
