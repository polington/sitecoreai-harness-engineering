## Title

Carousel Component

---

## Feature Overview

The Carousel component presents an ordered sequence of content panels in a single visual stage, showing exactly one active panel at a time. It is placed in the `headless-main` placeholder on the home page, just before the footer, and is driven by Sitecore-authored route and layout data. The component provides previous/next navigation, indicator-driven panel selection, optional autoplay with pause controls, and three presentation variants (default, hero, mini). Keyboard and screen-reader users receive full access to all controls and panel content.

---

## Design Intent

- Present authored panel content as the primary visual focus; chrome (indicators, navigation buttons) should complement rather than dominate the stage.
- Apply the design system's visual restraint principle: prefer fade transitions over slide animations, use neutral tones with minimal accent color for active states.
- The hero variant should feel immersive and edge-to-edge; the mini variant should feel compact and image-led; the default variant should feel balanced and contained within the page layout.
- All interactive controls must be visually discoverable but understated — icon-led buttons, small circular indicators, no heavy borders or shadows.
- Accessibility is first-class: every interactive state must have a visible focus ring, and every control must carry an accessible name.

## Page / Feature Structure

The Carousel occupies a single block-level region within the `headless-main` placeholder. Its internal structure consists of four regions stacked vertically:

1. **Stage region** — the primary visual area. Exactly one panel is visible at any time. Inactive panels are removed from view (not hidden behind the stage as a horizontal strip).
2. **Control row** — sits at the bottom of or immediately below the stage. Contains previous/next navigation buttons and the play/pause control when autoplay is configured.
3. **Indicator row** — a row of small circular markers, one per panel, centered below the control row in the default and mini variants, and left-aligned to the gutter in the hero variant on narrow screens.
4. **Panel content** — inside the stage, a panel may contain a full-bleed image, an image with an overlaid teaser, or another allowed content block. Panel content is composed through the delivery environment's content policy and is not defined by the Carousel itself.

In the hero variant the stage extends to the full viewport width. In the mini variant the stage extends to full width at a fixed height of approximately 400 px. In the default variant the stage is constrained by the surrounding layout container.

## Section Breakdown

### Stage Region

**Purpose:** Display the active panel content at the designed scale.

**Content:** One active panel at a time. The panel may contain a full-bleed image (with optional teaser overlay), or another allowed content block. When the carousel has no panels, the stage shows an authoring empty-state placeholder; in the published view it renders nothing and no navigation controls are shown.

**Visual guidance:** The stage background takes its dimensions from the variant rules. For image panels, the image fills the stage with cover cropping. The active panel should be fully opaque; the transition between panels uses a short cross-fade (opacity 0 → 1) rather than a slide. The transition duration should be short enough to feel responsive (100–200 ms is sufficient) and must not delay keyboard interaction.

**Interaction:** Pointer and keyboard actions on navigation controls or indicators trigger a panel change. Automatic transitions advance the panel after the configured delay when autoplay is active and the pause conditions are not met.

### Control Row

**Purpose:** House the previous, next, and play/pause buttons.

**Content:** 
- Previous button — icon-led (e.g. chevron left); text label may be visually hidden in compact layouts but must remain accessible.
- Next button — icon-led (e.g. chevron right); same treatment as Previous.
- Play/Pause button — visible only when autoplay is configured; its accessible label must reflect the current playback state ("Play" when paused, "Pause" when playing).

**Visual guidance:** Buttons are compact and placed at the edges of the control row (Previous left, Next right). Use the design system's minimal button style — no heavy borders, subtle hover state (slight colour shift or underline), clear focus ring. Controls do not change size or position on hover or focus.

**Interaction:** When only one panel is present, Previous and Next are hidden or visually inactive. The play/pause button is only present when autoplay is configured by the author.

### Indicator Row

**Purpose:** Show the position of all panels and allow direct panel selection.

**Content:** One small circular marker per panel. The active marker uses a darker/filled treatment; inactive markers use a lighter/outline treatment. On hover or focus, each marker provides visible feedback consistent with the design system's interaction style.

**Visual guidance:** Markers are centered below the stage in the default and mini variants. In the hero variant, on screens narrower than the design system's established breakpoint, markers shift to a left-aligned position within the page gutter. Marker size should be large enough to be a comfortable tap target (minimum 24 × 24 px touch area) without visually dominating the stage.

**Interaction:** Activating a marker makes its panel active and synchronises the active state of all markers and navigation buttons. Activating a marker while autoplay is user-paused must not restart autoplay.

### Panel Content Area

**Purpose:** Render the authored content for the active panel inside the stage.

**Content:** Determined entirely by the delivery environment's content policy. The Carousel does not prescribe inner markup. Common expected content is a full-bleed image or an image with an overlaid teaser (title, description, and a call-to-action link).

**Visual guidance:** For image panels, the image fills the stage with object-fit cover and a centered focal point. Teaser overlays should use sufficient contrast against the image (overlaid text on a semi-transparent scrim or equivalent) to meet WCAG AA contrast requirements. Panel title (when present) is used as the indicator label; when absent, a generated position label is used.

## Component Recommendations

- **Carousel container** — a single authored component registered in the component map. Receives the full authored field set (variant, autoplay settings, accessibility labels). Manages panel state and playback state client-side.
- **Panel slot** — a composable child slot within the Carousel. Each panel has a stable identity (used for active-state, accessibility relationships, and optional deep linking). Panel content is determined by the delivery environment's content policy.
- **Image primitive** — reuse the project's existing responsive image component for panel image rendering. This ensures cover cropping and focal-point behavior are consistent with the rest of the application.
- **Navigation buttons** — minimal icon buttons following the design system's button pattern. Reuse the existing button primitive if one exists; otherwise introduce a minimal icon-button sub-component scoped to the Carousel.
- **Indicator dots** — small interactive markers. No existing pattern exists for these; they should be implemented as a lightweight set of buttons with appropriate active/selected styling using design system color tokens.

## Responsive Behaviour

### Mobile (narrow — below the hero indicator breakpoint)

- **Default variant:** Stage fills the container width. Indicators are centered below the control row. Prev/next buttons are visible at the edges of the control row.
- **Hero variant:** Stage extends edge-to-edge (no horizontal inset). Indicators shift to left-aligned, aligned with the page gutter below the stage. Extra spacing is preserved below the carousel.
- **Mini variant:** Stage extends edge-to-edge at approximately 400 px height. Cover cropping keeps the image focal point centered.
- All interactive controls remain reachable and sufficiently sized for touch interaction.

### Tablet

- **Default variant:** Stage width follows the layout container. Indicators remain centered. Controls scale with the layout.
- **Hero variant:** Full-width stage. Indicators may return to centered layout if the screen width is above the hero indicator breakpoint.
- **Mini variant:** Full-width, fixed-height stage. Cover crop maintained.

### Desktop

- **Default variant:** Stage is constrained by the layout container. The control row and indicators sit below the stage. Previous/next controls are compact icon buttons aligned to the row edges.
- **Hero variant:** Full-viewport-width stage. Indicators centered below. Extra bottom spacing reinforces the immersive treatment.
- **Mini variant:** Full-width, fixed-height (~400 px) stage. Cover crop centered.

**Cross-breakpoint rules:**
- Stage width always follows its container or the viewport width (for hero/mini) — it must not shrink content into a narrow inset.
- Indicators and controls must remain visible and usable at all breakpoints.
- No horizontal overflow should occur at any viewport width.
- Image crops must preserve the subject and avoid distortion as the viewport changes.

## Accessibility Considerations

- **Carousel region:** The Carousel container should carry an accessible name sourced from an authored accessibility label field or a sensible default. Use an appropriate landmark or region role so screen-reader users can locate and skip the carousel.
- **Active panel announcement:** When the active panel changes (by any means), the change should be communicated to assistive technology without disrupting the reading flow. A live region or equivalent pattern is appropriate; the announcement should be concise (e.g. panel title or position label).
- **Panel state exposure:** Each panel must expose its ordinal position and active/inactive state. Panel identity must be stable and not change due to reorder operations.
- **Control accessible names:** Previous, Next, Play, and Pause buttons must have clear accessible names. The Play/Pause button's name must reflect the current state ("Play" / "Pause"). Indicator buttons must carry a meaningful label (panel title if available, otherwise a generated position label such as "Go to slide 2").
- **Keyboard operability:** All controls must be reachable via Tab and operable with Enter/Space. Indicators may also support left/right arrow key navigation within the indicator group. Focus must not be trapped inside the carousel. Automatic transitions must not move focus away from the user's current position.
- **Visible focus states:** Every interactive element must have a clearly visible focus ring following the design system's focus-state style. The focus state must be visually distinguishable from the active/selected indicator state.
- **Autoplay and motion:** The play/pause control satisfies the WCAG 2.2.2 (Pause, Stop, Hide) requirement for moving content. The document-hidden pause behavior ensures no transitions fire when the page is not visible.
- **Contrast:** Indicator active/inactive states, button icons, and any teaser overlay text must meet WCAG AA contrast ratios against their respective backgrounds.

## Risks

- **Hero variant edge-to-edge breakout:** The hero variant must override any constraining container padding on the home-page layout. If the layout uses a fixed-width container wrapper, the implementation will need a deliberate breakout technique. This should be confirmed and resolved during implementation planning.
- **Hero indicator breakpoint:** The specification requires indicators to shift to left-aligned on narrow screens for the hero variant. The design system does not define this specific breakpoint by name. The implementation should use the smallest named breakpoint (mobile/sm) as the threshold, or introduce a component-scoped token if needed. This decision should be locked during implementation planning.
- **Focus management during cross-fade:** A cross-fade transition that changes DOM visibility may interfere with focus if the outgoing panel contains a currently focused element. The implementation must ensure the transition does not move or trap focus.
- **Play/pause button visibility:** When autoplay is not configured, the play/pause button should not be rendered. Authors who later enable autoplay must see the button appear. The design should handle this gracefully without layout shift in the control row.
- **Teaser overlay contrast:** The contrast of teaser text overlaid on a full-bleed image depends on the image content, which is author-controlled. The design should include a semi-transparent scrim or gradient backing the overlay text to ensure consistent WCAG AA contrast regardless of image brightness.
