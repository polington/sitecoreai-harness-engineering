## Title

Accordion Component

---

## Feature Overview

The Accordion Component is a vertically stacked disclosure widget for the `headless-main` placeholder. It presents a list of up to 10 titled panels; visitors activate any header to reveal its content panel, and opening one panel automatically closes the previously open one (single-expansion, always on). The component will be placed on the home page immediately above the footer as the first author-placed main-content rendering.

---

## Design Intent

- **Scan-first layout.** All headers remain visible at all times; content is revealed on demand. The design should make it easy to read through all titles without opening a single panel.
- **WKND base treatment.** Styling follows the WKND accordion pattern: full-width rows, thin lower dividers, bold uppercase titles at approximately H4 scale, and a right-aligned plus/minus icon as a secondary state cue.
- **Content restraint.** The accordion sits inside the standard page container alongside other authored components. It must not introduce independent max-widths, horizontal overflow, or visual weight that competes with the surrounding content.
- **Design-system alignment.** Typography, spacing, and color draw exclusively from the existing design-system tokens. No new visual primitives are introduced.
- **Accessibility as a first-class concern.** State changes must be communicated structurally (layout) and semantically (ARIA), not by color alone.

## Page / Feature Structure

The accordion occupies a full-width block within the `headless-main` placeholder. Its outer boundary is the standard page container — it does not introduce its own horizontal constraints.

Structural regions from top to bottom:

1. **Item list** — ordered stack of disclosure rows, each consisting of a header and a conditionally visible content panel.
2. **Header row** — full-width clickable region containing the item title (left-aligned) and the state icon (right-aligned).
3. **Content panel** — revealed directly beneath its header when the item is expanded; hidden from view and the accessibility tree when collapsed.
4. **Empty state** — rendered only in the authoring environment when zero items are present; not visible in the published view.

The component has no independent heading, introductory copy, or footer element — those belong to the page composition, not the accordion itself.

---

## Section Breakdown

### Header Row

**Purpose:** Trigger row; the primary interaction surface for each accordion item.

**Expected content:** Author-supplied item title text.

**Visual guidance:**
- Full width of the containing column.
- No top or side borders; a thin lower divider separates rows and acts as the visual boundary.
- Approximately 1 em of vertical padding inside the header.
- Title: bold, uppercase, H4-scale (~20–22 px per design system heading scale). The heading level is author-configurable within the permitted hierarchy — the visual scale remains constant regardless of the semantic level chosen.
- State icon: plus (`+`) when collapsed, minus (`−`) when expanded, positioned at the far right of the header row. The icon is a secondary cue and must not be the sole indicator of expanded state.
- On hover: subtle visual feedback (e.g., slight background tint or color shift) without changing row height, moving the icon, or altering the title position.
- On activation (pressed/toggling): immediate state feedback before the panel motion completes.

**Interaction:** Activating the header toggles its associated panel. Because single-expansion is always active, activating a header also collapses the previously open panel.

---

### Content Panel

**Purpose:** Reveals the authored body content for the item.

**Expected content:** Rich text including nested paragraphs, links, images, lists, and other allowed content blocks.

**Visual guidance:**
- Appears directly beneath its parent header.
- Slight left indent relative to the header title to create visual belonging.
- Body typography (~16–18 px, generous line height per design system).
- Small top offset separating the panel content from the header.
- Short fade-in or height-reveal transition on open; collapsed panels are removed from the visible layout.

**Interaction:** Panel content is inert when collapsed. When expanded, all interactive elements within the panel (links, buttons) are reachable and functional.

---

### Empty State (Authoring Only)

**Purpose:** Provides a clear authoring placeholder when the accordion has no items.

**Expected content:** A brief label or affordance indicating the component is present but has no items yet (e.g., "No accordion items added").

**Visual guidance:** Minimal; this region is never visible in the published view.

## Component Recommendations

- **Accordion container** — a single authored component registered in the component map for `headless-main`. Renders the ordered item list and manages which panel is currently open.
- **Accordion item** — a child composition unit, each holding a header and a content panel. Items are ordered and identified by stable keys derived from their Sitecore item IDs.
- **Disclosure control** — the interactive header element. Should expose the correct ARIA role and attributes natively or via explicit ARIA markup.
- **Rich-text or content region** — reuse the existing rich-text rendering pattern for panel body content; do not introduce a new content primitive.

All components should use design-system spacing tokens and typography scales rather than hard-coded values.

## Responsive Behaviour

### Mobile (up to ~640 px, reference 390 px viewport)

- Accordion rows remain full width within the page container.
- Long item titles wrap onto multiple lines; the state icon remains right-aligned and does not collapse into the title area.
- The tap target for each header spans the full row width, not just the text.
- Panel content reflows naturally at narrow widths; line length and spacing remain readable.
- No horizontal scroll is introduced.

### Tablet (~640 px – ~1024 px)

- Behavior and layout are identical to mobile; the accordion simply gains more horizontal room.
- Content within expanded panels may reach comfortable reading width without additional constraints.

### Desktop (> ~1024 px)

- The accordion respects the page container's max-width; it does not stretch beyond the standard content column.
- Row density and visual treatment remain the same as at smaller breakpoints.

### Cross-breakpoint rules

- The plus/minus icon must remain visible and aligned at all widths.
- Expanding or collapsing a panel changes page height but must not cause the header title or state icon to shift horizontally.
- No minimum desktop width is assumed; the component must be usable at any viewport that fits the container.

## Accessibility Considerations

- **Heading semantics.** Each item title is rendered as a heading at the author-configured level. The visual scale remains H4-equivalent regardless of the semantic level chosen. Configurable levels must stay within the permitted design-system heading hierarchy (H2–H4 is a reasonable constraint; the implementation plan should confirm).
- **Disclosure control.** The interactive element within each header must expose `aria-expanded` (true when open, false when closed) and `aria-controls` referencing the associated panel's ID.
- **Panel visibility.** Collapsed panels must be removed from the accessibility tree and normal tab order. The `hidden` attribute or equivalent disclosure semantics should be used.
- **Keyboard operation.** All headers must be reachable via Tab and activatable via Enter and Space. Focus order follows DOM order (top to bottom). Focus must not jump to an unexpected location after opening or closing a panel.
- **Focus visibility.** Keyboard focus on a header must have a clear visible focus indicator that is not conveyed by color alone (outline or equivalent treatment).
- **State communication.** The expanded/collapsed state must be communicated by both structural change (panel appears/disappears) and ARIA attributes. The plus/minus icon is supplemental.
- **Contrast.** Header text, dividers, and state icons must meet the design system's contrast requirements against their backgrounds.
- **Single-expansion transition.** When a new item opens and the previous item closes, both state changes must be reflected immediately in ARIA attributes and DOM structure so that assistive technology users perceive the correct state.

## Risks

- **Heading-level misconfiguration.** If the author selects a heading level that skips levels in the document outline (e.g., H4 directly after H1), the page structure becomes inaccessible. The authoring interface or component may need to display guidance, though enforcement is editorial rather than technical.
- **Long titles and icon alignment.** At narrow viewports, multi-line titles could cause the icon to align with the wrong visual line. The layout must pin the icon to the top-right of the header row, not the center.
- **Panel transition and layout shift.** A height-based reveal transition can cause content below the accordion to reflow, potentially disorienting users. The transition should be short (100–200 ms) and the implementation plan should confirm the approach.
- **Single-expansion with multiple initial items.** The spec resolves this as first-in-list wins; the design is consistent with this — only one panel is ever shown open at initial render.
- **Rich content in panels.** Images or wide tables inside panels may overflow the panel width at narrow viewports. Standard responsive media patterns from the existing content pipeline should handle this; no accordion-specific fix is expected.
