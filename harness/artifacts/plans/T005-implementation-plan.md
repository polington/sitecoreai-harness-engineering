## Technical Approach

### Overview

This task delivers two components to the rendering host:

1. **PromoCardGrid** — a container component that receives a multi-value field
   (Multilist/Treelist) referencing Promo Card data source items and renders them in a
   responsive CSS Grid layout (1/2/3 columns at mobile/tablet/desktop).
2. **promoCard** — a presentational sub-component (not independently Sitecore-rendered)
   that renders a single card's image, title, description, and optional CTA link.

Both live within a single `PromoCardGrid/` folder under `src/components/`. The
`PromoCardGrid.tsx` file is the only PascalCase-named file at the folder root and is
the registered Sitecore rendering. The presentational card component uses a camelCase
file name (`promoCard.tsx`) to avoid being registered as a separate Sitecore component
map entry.

The Sitecore rendering definition, data source templates, placeholder settings, and
available renderings configuration are CMS-side work executed by a human operator and
documented in the CMS Configuration Guide (T005 CMS stage). The Build agent is
responsible only for the rendering-host code.

### Component Model

The **PromoCardGrid** component is a **server component** — no client-side state or
browser APIs are required. The multi-value field arrives as an array of resolved item
references in layout data. The component iterates the array and renders a `promoCard`
for each item.

The component lives at:

```
src/headapps/rob-harness-engineering/src/components/PromoCardGrid/PromoCardGrid.tsx
```

`PromoCardGrid.tsx` is the only file in this folder with a PascalCase base name. It
will be registered by `sitecore-tools:generate-map` as component key `PromoCardGrid`.
The Sitecore rendering item's **Component Name** field must match this key exactly.

Supporting files use camelCase names to avoid unintended component map registrations
(matching the established Header and HeroBanner folder conventions):

- `promoCardGridTypes.ts` — TypeScript interfaces for all fields and props
- `promoCard.tsx` — Presentational sub-component for a single card
- `__tests__/PromoCardGrid.test.tsx` — Component tests (excluded from component map
  scan by the `src/components/**/__tests__/*` exclusion in `sitecore.cli.config.ts`)

### Multi-Value Field Data Shape

The Promo Card Grid data source has a Multilist or Treelist field that references
Promo Card items. In Sitecore Content SDK layout data, multi-value reference fields
resolve as an array of objects, each containing the referenced item's fields. The
PromoCardGrid component receives this array and maps over it to render individual
cards.

The expected data shape for the multi-value field is an array where each element has a
`fields` property containing the Promo Card's authored fields (Image, Title,
Description, Link). The TypeScript types will model this shape using SDK primitives.

### Presentational Card Sub-Component

The `promoCard.tsx` sub-component is purely presentational. It receives a single card's
fields as props and renders the card's visual structure:

1. Image at the top with 16:9 aspect ratio via `object-cover`
2. Title as an `<h3>` heading
3. Description as body text
4. Optional CTA link (rendered only when the link field has a non-empty href)

The card uses the Sitecore `Image` and `Link` SDK primitives for field rendering,
consistent with the HeroBanner pattern.

### Grid Layout

The grid uses CSS Grid (Tailwind utilities) for the responsive column layout:

- Mobile: `grid-cols-1`
- Tablet: `md:grid-cols-2`
- Desktop: `lg:grid-cols-3`

Gap between cards uses design-system spacing tokens (`gap-4` at mobile, `gap-6` at
tablet/desktop). Equal card heights within rows are achieved by default CSS Grid
behaviour (items stretch to fill the implicit row height).

### Semantic Structure

The design note specifies the grid should use a `<ul>` / `<li>` list structure so
assistive technologies announce the collection and item count. Each card is wrapped in
an `<li>`. The grid container renders as a `<ul>` with the CSS Grid layout applied.

When zero cards are referenced, the component renders nothing — no empty `<ul>`, no
empty wrapper. This matches the empty-state requirement.

### Section Wrapper

The grid section uses a standard outer wrapper with vertical spacing consistent with
adjacent page sections (`py-10` to `py-16`). A constrained-width, centred container
(`max-w-7xl mx-auto px-4 sm:px-6 lg:px-8` or equivalent site container pattern) holds
the grid. This matches the existing container patterns in the headapp.

### Layout.tsx Relationship

`Layout.tsx` wraps the `headless-main` placeholder in a `<main>` element with a
container `<div id="content">`. The PromoCardGrid component renders inside this
container. The component does not add `<main>` or `<section>` landmarks that would
conflict — it uses a `<section>` element as the outermost wrapper (appropriate for a
self-contained content block within `<main>`).

### CTA Link

The CTA is rendered using the SDK `Link` primitive from `@sitecore-content-sdk/nextjs`.
When the General Link field is empty or has no `href`, the component renders nothing
for the CTA — no empty anchor, no placeholder text, no empty wrapper.

The CTA is styled as a text link with visible hover and focus states. A focus ring
meeting WCAG 2.1 contrast requirements is applied.

### Test Framework

Jest and React Testing Library are already installed and configured (`jest.config.js`,
`jest.setup.ts` exist; test infrastructure established by T001). No test framework
setup is needed for this task.

3. **Write `promoCard.tsx`.**
   Server component (no `'use client'`). Structure:

   - Accept `PromoCardFields` as props.
   - Render the card as a `<div>` (or `<article>`) with card styling: neutral surface
     background, subtle border or light shadow, internal padding using design-system
     spacing tokens, full height via `h-full` and flex column layout to keep the CTA
     anchored at the bottom.
   - Render the image using the Sitecore `Image` field primitive with a wrapper
     enforcing 16:9 aspect ratio (`aspect-video` or equivalent) and `object-cover`.
   - Render the title as an `<h3>` with the design-system heading scale.
   - Render the description as a `<p>` with body text sizing.
   - Conditionally render the CTA: check whether the `Link` field has a value with a

4. **Write `PromoCardGrid.tsx`.**
   Server component (no `'use client'`). Structure:

   - Guard with `if (!fields?.Cards?.length) return null` at the top (empty state:

   - Render an outer `<section>` element with vertical spacing classes (`py-10` to
     `py-16`).
   - Inside, render a constrained-width container `<div>` centred on the page with
     horizontal padding (matching the site container pattern).
   - Render a `<ul>` element with CSS Grid classes: `grid grid-cols-1 md:grid-cols-2

   - Map over `fields.Cards`, rendering each item as an `<li>` wrapping the `promoCard`

## Risks

### R1 — Multi-Value Field Data Shape

The Multilist/Treelist field on the PromoCardGrid data source must resolve as an array
of objects containing the referenced items' fields in layout data. This is standard
XM Cloud behaviour for reference fields with datasource resolution, but the exact
shape should be validated against real layout data during integration.

**Mitigation:** The types file models the expected shape as
`Array<{ fields: PromoCardFields }>`. If the runtime shape includes additional
wrapper properties (e.g. `id`, `name`, `url`), the Build agent should extend the type
accordingly. If fields are not resolved inline and require a separate GraphQL query,
escalate to the orchestrator as this changes the architectural approach.

### R2 — Component Map Pollution

`sitecore-tools:generate-map` will register `promoCard` and `promoCardGridTypes` as
component entries. These are harmless dead entries that do not correspond to any
Sitecore rendering definition and will not cause runtime errors.

**Mitigation:** No action needed. This is consistent with the existing behaviour for
`headerTypes`, `heroBannerTypes`, and other supporting files.

### R3 — Large Card Counts

The specification explicitly states that pagination and "load more" are out of scope.
If an author references a large number of cards (20+), the grid will render them all,
which may cause performance degradation on page load due to numerous images.

**Mitigation:** This is a known accepted limitation per the spec. The Build agent should
not add pagination or lazy-loading logic beyond what Next.js Image provides natively
(lazy loading by default). If performance concerns surface during QA, they can be
addressed in a future task.

### R4 — Image Aspect Ratio Consistency

The design note recommends a 16:9 aspect ratio enforced via CSS (`object-cover`). Images
with extreme source aspect ratios will be cropped. This is an accepted trade-off per
the design note.

**Mitigation:** No action needed beyond implementing the `object-cover` approach. The
cropping behaviour is by design.
