## Technical Approach

### Overview

The rendering-host work for this task is a single Sitecore Content SDK rendering
component — `SiteFooter` — placed in the `headless-footer` placeholder that `Layout.tsx`
already exposes. The component receives its logo, navigation links, social links, and
copyright text via Sitecore Content SDK component fields (layout data), renders them
using SDK field primitives, and applies Tailwind CSS utilities for the three-column
desktop / single-column mobile responsive layout.

The SXA Footer Partial Design, Default Page Design update, and all Sitecore item
configuration are CMS-side work executed by a human operator and documented in the
CMS Configuration Guide (T002 CMS stage). The Build agent is responsible only for the
rendering-host code.

### Component Model

The `SiteFooter` component is a **server component** — no client-side state is needed
for the footer (unlike the Header's hamburger toggle). The absence of `'use client'`
is intentional and should be preserved.

The component lives at:

```
src/headapps/rob-harness-engineering/src/components/SiteFooter/SiteFooter.tsx
```

`SiteFooter.tsx` is the only file in this folder with a PascalCase base name. It will
be registered by `sitecore-tools:generate-map` as component key `SiteFooter`. The
Sitecore rendering item's **Component Name** field must match this key exactly.

Supporting files use camelCase names to avoid unintended component map registrations
(matching the established Header folder convention):

- `footerTypes.ts` — TypeScript interfaces for fields and props
- `footerLogo.tsx` — Logo image + home-page link sub-component
- `footerNav.tsx` — Navigation link list sub-component
- `footerSocialLinks.tsx` — Social platform link sub-component
- `__tests__/SiteFooter.test.tsx` — Component tests (excluded from component map
  scan by the `src/components/**/__tests__/*` exclusion in `sitecore.cli.config.ts`)

### Semantic HTML and Layout.tsx Relationship

`Layout.tsx` already wraps the `headless-footer` AppPlaceholder in a `<footer>` HTML
landmark element and a `<div id="footer">` container (confirmed by codebase
inspection). This is the same pattern established for `headless-header`: Layout
provides the outer landmark; the component renders its internal structure within it.

Therefore, the `SiteFooter` component must **not** add a redundant `<footer>` wrapper.
Its outermost element should be a container `<div>` that provides the design system
layout (max-width container, padding). This mirrors how `Header.tsx` renders a `<div>`
rather than a `<header>`.

The `<footer>` landmark requirement in AC-09 is satisfied at the page level by
`Layout.tsx`. The `<nav aria-label="Footer navigation">` landmark remains the direct
responsibility of the `SiteFooter` component and must be present in its rendered
output. No change to `Layout.tsx` is required.

### Navigation Data Model

The footer's secondary navigation links follow the same field-and-shape convention
established by the Header component. The `NavigationLinks` field on the data source
template is a Multilist/Treelist whose items each carry a single General Link field
(`Link`). The component maps over the `NavigationLinks` array, and each item has the
shape `{ fields: { Link: LinkField } }`.

This aligns with the `NavigationLinkItem` interface already defined in `headerTypes.ts`.
The footer defines its own equivalent interface in `footerTypes.ts` rather than
importing from the Header folder, keeping the two components independently deployable.

### Social Links

No SVG icon library is present in `package.json` (confirmed by inspection — no
heroicons, lucide-react, react-icons, or equivalent). The social link implementation
therefore uses **text-only links with `aria-label`** as the accessible name. Each
social anchor renders the platform name as visible text (e.g. "Facebook", "X (Twitter)",
"LinkedIn") and carries `aria-label` on the anchor element for explicit naming. This
is the design-compliant fallback prescribed in both the feature spec and design note.

`target="_blank"` is applied by the component, not by the author. Conditional rendering
per platform field is required: a General Link field that is empty or null must produce
no anchor element.

### Placeholder Registration

`headless-footer` is already registered as an `AppPlaceholder` in `Layout.tsx`
(confirmed by codebase inspection). No changes to `Layout.tsx`, `sitecore.config.ts`,
or any other existing file are needed to register the placeholder for local development.

### Mobile Breakpoint

The Header component uses Tailwind's `lg:` breakpoint prefix for its responsive
behaviour (`hidden lg:flex`). The SiteFooter should follow the same convention:
single-column (stacked) layout at widths below `lg`, three-column layout at `lg` and
above. This produces a consistent breakpoint experience across the page header and
footer.

### Column Proportions

The three-column desktop grid uses equal thirds (`grid-cols-3` or equivalent Tailwind
flex/grid utilities). Equal distribution is the simplest defensible default for a
logo/nav/social split and is consistent with the design note's intent of
"proportionally balanced" columns.

### Copyright Bar

The copyright text renders as a full-width block below the three-column row,
using the design system's supporting text size and muted colour tokens. It is
non-interactive and contains no focusable elements.

## Implementation Steps

1. **Create the `SiteFooter/` component folder** at  
   `src/headapps/rob-harness-engineering/src/components/SiteFooter/`.

2. **Write `footerTypes.ts`.**  
   Define `SiteFooterFields` (containing `Logo: ImageField`,
   `NavigationLinks: NavigationLinkItem[]`, `FacebookLink: LinkField`,
   `TwitterLink: LinkField`, `LinkedInLink: LinkField`,
   `CopyrightText: TextField`) and `SiteFooterProps` (wrapping
   `fields?: SiteFooterFields`). Import all field types from
   `@sitecore-content-sdk/nextjs`. Define a local `NavigationLinkItem` interface
   matching the shape `{ fields: { Link: LinkField } }`.

3. **Write `footerLogo.tsx`.**  
   Render a `next/link` `<Link>` anchor wrapping the Sitecore `<Image>` field
   primitive. Home href defaults to `'/'`. Follow `headerLogo.tsx` as the reference
   pattern. Include an `aria-label` on the anchor (e.g. `"Go to homepage"`) and
   ensure the Image field is rendered with its authored alt text.

4. **Write `footerNav.tsx`.**  
   Render a `<nav aria-label="Footer navigation">` containing a `<ul>` whose `<li>`
   elements each hold a Sitecore `<Link>` field primitive. Return `null` when the
   `links` array is empty or absent. Follow `headerNav.tsx` as the reference pattern
   for the field-rendering loop.

5. **Write `footerSocialLinks.tsx`.**  
   Accept `facebook`, `twitter`, and `linkedIn` props, each typed as
   `LinkField | undefined`. For each platform, conditionally render an `<a>` element
   only when the corresponding field value is non-empty (has a truthy `href`). Each
   anchor carries `target="_blank"`, `rel="noopener noreferrer"`, and an `aria-label`
   naming the platform (e.g. `aria-label="Visit us on Facebook"`). Visible text
   content renders the platform name. A falsy or empty field produces no DOM output
   for that platform.

6. **Write `SiteFooter.tsx`.**  
   Server component (no `'use client'`). Guard with `if (!fields) return null` at
   the top. Render a responsive container `<div>` as the outermost element (do not
   add `<footer>` — `Layout.tsx` already provides the landmark). Inside, render a
   three-column grid that is single-column by default (mobile-first) and becomes
   three-column at the `lg:` breakpoint. Place `footerLogo.tsx`, `footerNav.tsx`, and
   `footerSocialLinks.tsx` in the three respective columns. Render the copyright bar
   as a full-width block below the column row, driven by the `CopyrightText` TextField.
   Use Tailwind utilities drawn from the design system's spacing scale, colour tokens,
   and typography tokens throughout.

7. **Write `__tests__/SiteFooter.test.tsx`.**  
   Set up the same SDK and `next/link` mocks used in `Header.test.tsx`. Define a
   `makeProps` helper covering all fields. Write the following test cases, one per
   `it` block:
   - Logo image renders from the authored Image field and its anchor links to `'/'`.
   - Navigation links reflect the authored `NavigationLinks` array (assert rendered
     links match the input list, not a hard-coded string).
   - Facebook social link renders with `target="_blank"` and a non-empty `aria-label`.
   - X (Twitter) social link renders with `target="_blank"` and a non-empty `aria-label`.
   - LinkedIn social link renders with `target="_blank"` and a non-empty `aria-label`.
   - A social link whose field value is empty/null produces no anchor element for that
     platform.
   - Copyright text renders the full authored field value.
   - A `<nav>` with `aria-label="Footer navigation"` is present in the rendered output.
   - The outermost container applies the single-column stacking class when the column
     wrapper is inspected (assert the presence of the mobile-first layout structure via
     the appropriate class or DOM structure that represents the stacking behaviour).
   - `SiteFooter` renders nothing (returns null) when the `fields` prop is absent.

8. **Run `sitecore-tools:generate-map`.**  
   Execute `npm run sitecore-tools:generate-map` from the head app directory. Verify

## Risks

### R1 — Default Page Design Impact

Adding the Footer Partial Design to the Default Page Design will introduce a footer
region on every page currently using that design. Pages that previously rendered no
footer chrome will gain one. The visual impact on all existing authored pages must be
confirmed during QA before the task is approved.

**Mitigation:** Document this explicitly in the QA checklist and CMS Configuration
Guide. The human operator performing the CMS Configuration step should review at least
two representative pages in a staging environment before sign-off.

---

### R2 — NavigationLinks Field Type Mismatch

The plan assumes the `NavigationLinks` Link List field serialises in Sitecore layout
data as `{ fields: { Link: LinkField } }[]`, matching the Header convention. If the
exact Sitecore template field type chosen during CMS Configuration produces a different
shape in the rendered layout data, the component will fail to render navigation links
at runtime.

**Mitigation:** The Build agent should confirm the field type matches the Header
pattern before finalising `footerTypes.ts`. If a mismatch is discovered, escalate to
the orchestrator before raising a fix.

---

### R3 — Placeholder Key Mismatch (CMS-side)

The `headless-footer` placeholder key used in the Footer Partial Design configuration
in Sitecore must exactly match the key registered in `Layout.tsx`
(`name="headless-footer"`). The key is already confirmed correct in the rendering host
(Layout.tsx), but the CMS operator must use the identical string when configuring the
Partial Design.

**Mitigation:** The CMS Configuration Guide must state the exact key string with
emphasis. The post-configuration validation step must verify the footer renders in a
live environment.

---

### R4 — Component Map Pollution

`sitecore-tools:generate-map` registers every non-excluded file base name in
`src/components/` as a component entry. The camelCase sub-component files
(`footerTypes`, `footerLogo`, `footerNav`, `footerSocialLinks`) will appear as
component entries in the generated map but will not correspond to any Sitecore
rendering definition. This produces harmless dead entries in the map.

**Mitigation:** These entries are non-functional and do not cause runtime errors. No
exclusion rules are added unless the project's component map policy changes.
The Build agent should flag these entries in the run report so they are visible.

---

### R5 — `SiteFooter` Does Not Emit a `<footer>` Element

The SiteFooter component's outermost element is a `<div>`, not `<footer>`, because
`Layout.tsx` already provides the `<footer>` landmark. This diverges from the literal
wording of AC-09 ("The outermost element of the Site Footer rendering is a `<footer>`
landmark element") but is semantically equivalent: the page still exposes a
`contentinfo` landmark via Layout.

**Mitigation:** The QA agent must be made aware of this decision. The test for AC-09
should verify the presence of a `<nav aria-label="Footer navigation">` within the
component's rendered output rather than asserting that the component itself emits a
`<footer>` element. The CMS Configuration Guide should note that the `<footer>`
landmark is provided by Layout.tsx.
