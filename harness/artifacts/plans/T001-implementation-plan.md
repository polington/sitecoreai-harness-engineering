## Technical Approach

### Overview

The rendering-host work for this task is a single Sitecore JSS rendering component —
`Header` — placed in the existing `headless-header` placeholder that `Layout.tsx`
already exposes. The component receives its logo and navigation data via Sitecore
Content SDK component fields (layout data), renders them using SDK field primitives,
and manages mobile navigation open/close state as local React state.

The SXA Partial Design, Default Page Design, and all Sitecore item configuration are
CMS-side work executed by a human operator and documented in the CMS Configuration
Guide (T001 CMS stage). The Build agent is responsible only for the rendering-host
code.

### Component Model

The `Header` component is a **client component** (`'use client'`). The hamburger menu
toggle requires `useState`, which precludes server-component rendering for the
interactive layer. The component lives at:

```
src/headapps/rob-harness-engineering/src/components/Header/Header.tsx
```

It is the **only file in this folder whose base name** will be registered as a Sitecore
component entry by `sitecore-tools:generate-map`. The component map key will be
`Header`, and the Sitecore rendering item's Component Name field must match exactly.

Supporting files in the same folder use camelCase names to avoid unintended component
map collisions:

- `headerTypes.ts` — TypeScript interfaces for fields and props
- `headerLogo.tsx` — Logo sub-component
- `headerNav.tsx` — Navigation sub-component
- `__tests__/Header.test.tsx` — component tests

### Semantic HTML Note

`Layout.tsx` already wraps the `headless-header` placeholder in a `<header>` element.
The `Header.tsx` component must **not** add a redundant `<header>` wrapper. The
component renders its interior content directly within the existing `<header>` landmark
provided by `Layout.tsx`.

### Navigation Data Model

The `Header` rendering receives navigation items via a Sitecore Multilist field
(`NavigationLinks`) on the component's data source item. Each item in the list has a
single General Link field (`Link`) that provides the display text and target URL. This
model is directly supported by the Content SDK's field rendering primitives and avoids
any custom data-fetching logic.

The component maps over the `NavigationLinks` array and renders each link using the
SDK's `<Link>` field primitive.

### Responsive Toggle

The mobile navigation open/close state is managed with `useState` in `Header.tsx`.
Tailwind CSS conditional classes (`hidden`, `block`, responsive prefixes like `lg:flex`,
`lg:hidden`) control visibility at each breakpoint. No JS-driven resize listeners are
needed.

The desktop breakpoint is `lg` (1024px), as recommended in the design note.

### Test Framework

No testing framework is currently installed in the head app. Jest and React Testing
Library must be added as dev dependencies before component tests can be written. The
configuration should use `next/jest` to get the correct Next.js transform settings.

### Step 4 — Implement the Navigation sub-component (headerNav.tsx)

Create `src/components/Header/headerNav.tsx`:

- Accept `links: NavigationLinkItem[]` and `isOpen: boolean` as props.
- Render a `<nav>` element with `aria-label="Primary"`.
- Inside, render the navigation link list. Each link uses the Content SDK `<Link>`
  field primitive to render the `LinkField` value (which supplies both the display text
  and href from Sitecore data).
- Apply responsive Tailwind classes:
  - On `lg` and above: horizontal flex row, always visible.
  - Below `lg`: vertical stack, shown/hidden based on `isOpen`.
- If `links` is empty or undefined, render nothing (no hardcoded placeholder links).

### Step 5 — Implement the main Header component (Header.tsx)

Create `src/components/Header/Header.tsx`:

- Add `'use client'` directive (required for `useState`).
- Import `HeaderProps` from `headerTypes.ts`, `headerLogo` and `headerNav` sub-components.
- Manage `isOpen: boolean` state with `useState(false)`.
- Render:
  1. A container `<div>` (not `<header>` — the semantic landmark is already provided by

  2. Inside: a flex row with `headerLogo` on the left and, on desktop, `headerNav`
     inline.
  3. A hamburger toggle `<button>` visible only below `lg` breakpoint:
     - `aria-label` set dynamically: `"Open navigation"` when closed, `"Close

     - On click: toggle `isOpen`.
     - Keyboard: `<button>` natively responds to Enter and Space.
  4. `headerNav` rendered with `isOpen` prop for mobile visibility control.
- Guard `props.fields` — if absent (e.g., rendering without a data source), render
  nothing rather than throwing.

## Risks

1. **No test framework installed**: Jest and React Testing Library must be installed and
   configured before tests can run. The configuration requires `next/jest` for correct
   App Router compatibility. An incorrect Jest config could cause module-resolution
   failures for Next.js imports inside tests.

2. **Nested `<header>` semantic error**: `Layout.tsx` already wraps `headless-header` in
   `<header>`. If the Build agent adds another `<header>` in `Header.tsx`, the output
   will contain nested `<header>` elements, which is invalid HTML. The plan explicitly
   disallows this; the Build agent must follow this constraint.

3. **Component map auto-registration of sub-component files**: `headerLogo.tsx`,
   `headerNav.tsx`, and `headerTypes.ts` will all be registered in the component map by
   `sitecore-tools:generate-map`. Their entries (`headerLogo`, `headerNav`,
   `headerTypes`) are harmless as long as no Sitecore rendering items use those component
   names. This is an expected and acceptable consequence of the scan model.

4. **Tailwind v4 responsive class syntax**: The project uses Tailwind CSS v4 (`^4`).
   Tailwind v4 changed its configuration model from v3. Responsive prefix classes
   (`lg:hidden`, `lg:flex`) should still work the same way. The Build agent should verify
   that responsive Tailwind classes render correctly and that no v4-specific config
   changes are needed for the breakpoint.

5. **SDK Image and Link field primitive names**: The Content SDK 2.x (`~2.0.2`) may use
   slightly different component names or import paths from the JSS 21.x era (e.g.,
   `JssImage` vs `Image`, `JssLink` vs `Link`). The Build agent should confirm the
   correct import from `@sitecore-content-sdk/nextjs` before writing the component.

6. **React 19 + Testing Library compatibility**: The project uses React 19 (`^19.2.1`).
   Some versions of `@testing-library/react` may require a specific peer dependency
   version for React 19. The Build agent should install the latest RTL release and
   verify compatibility at install time.

1. The `src/Layout.tsx` `<header>` wrapper around `headless-header` is the canonical
   semantic `<header>` landmark for the page. The `Header.tsx` rendering component does
   not add its own `<header>` element.

2. The `sitecore.cli.config.ts` component map scan path (`src/components/`) and
   exclusion (`src/components/content-sdk/*`) remain unchanged by this task.

3. The existing serialization module (`src/authoring/items/nextjs-starter.module.json`)
   already covers the paths where new Sitecore items (templates, renderings, placeholder
   settings) will be created. No module.json changes are required.

4. Tailwind CSS v4 responsive prefix classes work without additional breakpoint
   configuration for the standard `lg` breakpoint (1024px).

5. The `@sitecore-content-sdk/nextjs` v2.x package exposes Image and Link field
   rendering primitives suitable for use in client components.

6. The desktop navigation breakpoint is `lg` (1024px) as defined in the design note.
   Below `lg`, the hamburger pattern applies; at `lg` and above, the full navigation bar
   is visible.

7. Navigation link items on the `NavigationLinks` multilist field contain a `Link`
   (General Link field) that supplies both the rendered link text and the target URL.
