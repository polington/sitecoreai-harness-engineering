## Technical Approach

### Overview

The rendering-host work for this task is a single Sitecore Content SDK rendering
component — `HeroBanner` — placed in the `headless-main` placeholder that `Layout.tsx`
already exposes inside a `<main>` element. The component receives its heading,
subheading, background image, CTA link, and overlay opacity via Sitecore Content SDK
component fields (layout data), renders them using SDK field primitives, and applies
Tailwind CSS utilities for the full-width, fixed-height layered composition.

The Sitecore rendering definition, data source template, placeholder settings, and
available renderings configuration are CMS-side work executed by a human operator and
documented in the CMS Configuration Guide (T004 CMS stage). The Build agent is
responsible only for the rendering-host code.

### Component Model

The `HeroBanner` component is a **server component** — no client-side state is required.
The hero banner has no interactive toggle, form input, or browser-API dependency. The
CTA link is a standard anchor rendered by the SDK `Link` primitive. The absence of
`'use client'` is intentional and must be preserved.

The component lives at:

```
src/headapps/rob-harness-engineering/src/components/HeroBanner/HeroBanner.tsx
```

`HeroBanner.tsx` is the only file in this folder with a PascalCase base name. It will
be registered by `sitecore-tools:generate-map` as component key `HeroBanner`. The
Sitecore rendering item's **Component Name** field must match this key exactly.

Supporting files use camelCase names to avoid unintended component map registrations
(matching the established Header and SiteFooter folder conventions):

- `heroBannerTypes.ts` — TypeScript interfaces for fields and props
- `__tests__/HeroBanner.test.tsx` — Component tests (excluded from component map scan
  by the `src/components/**/__tests__/*` exclusion in `sitecore.cli.config.ts`)

### No Sub-Components

The design note explicitly recommends no sub-components. The hero banner's internal
structure (background image, overlay scrim, heading, subheading, CTA) is simple enough
to be rendered directly within the single `HeroBanner` component. Introducing
sub-components would add organisational overhead without reuse benefit.

### Semantic HTML and Layout.tsx Relationship

`Layout.tsx` wraps the `headless-main` placeholder in a `<main>` element with a
container `<div id="content">`. The HeroBanner component renders inside this container.
The component does not add `<main>` or `<section>` landmarks — it is a content
component within the existing `<main>` region, not a page-level structural element.

The heading is rendered as an `<h1>` element as required by the specification. The
subheading uses a `<p>` element (not `<h2>`) to preserve heading hierarchy for
subsequent page content, as confirmed in the design note.

### Background Image Approach

The Sitecore Content SDK `Image` component (from `@sitecore-content-sdk/nextjs`)
renders an `<img>` element with the authored `alt` attribute from the Sitecore Image
field. This is the correct approach for the hero banner because:

1. It preserves the authored `alt` text behaviour (meaningful vs. decorative).
2. It integrates with Sitecore Experience Editor for field-level editing.
3. It can be styled with `object-fit: cover` and absolute positioning to achieve the
   full-width, fixed-height background effect.

The image is rendered as a positioned `<img>` element within a `relative` container,
styled with `absolute inset-0 w-full h-full object-cover` to fill the banner area.
This avoids the CSS `background-image` approach entirely, preserving SDK field
rendering, alt text, and Experience Editor compatibility.

The container uses a fixed height of `h-[60vh]` with a `min-h-[400px]` safety minimum
to prevent the banner from becoming too short on landscape mobile viewports (addressing
the design note's risk about short viewports).

### Full-Width Breakout

The `headless-main` placeholder renders inside `<main><div id="content">`. The hero
banner must break out of this container to span the full viewport width. The breakout
technique uses `w-screen` combined with negative margin and relative positioning
(`relative left-1/2 right-1/2 -ml-[50vw] -mr-[50vw] w-screen`) applied to the
outermost wrapper of the HeroBanner component. This is a well-established CSS pattern
that works regardless of the parent container's max-width or padding.

If the parent `<div id="content">` has `overflow: hidden`, this technique may clip the
hero. The Build agent should verify that no `overflow` constraint exists on the parent
and flag it if found.

### Overlay Scrim

The scrim is a `<div>` positioned absolutely over the background image, behind the text
content, using a dark background colour at a configurable opacity. The overlay opacity
is driven by the `OverlayOpacity` field from the data source.

The component enforces a minimum opacity of 30% programmatically (as specified in the
design note) — if the authored value is below 30, it is clamped to 30. When no value
is authored, the default is 40% (within the 40–50% range specified in the design note).

The overlay opacity field type recommendation is a **Droplink** field offering preset
values (30, 40, 50, 60, 70, 80). This prevents invalid input and simplifies the
authoring experience. The Droplink references a folder of option items under
`/sitecore/content/harness-engineering/[site]/Data/HeroBanner/Overlay Opacity Options`.
Each option item has a `Value` field (Single-Line Text or Number) containing the
numeric opacity percentage.

At the rendering-host level, the component reads the selected option's value, parses
it as a number, applies the 30% minimum clamp, and renders it as an inline style
(`opacity: {value / 100}`) on the scrim `<div>`. Inline style is appropriate here
because the opacity is a dynamic, author-controlled value — not a design-system token
that can be mapped to a static Tailwind class.

### CTA Link

The CTA is rendered using the SDK `Link` primitive from `@sitecore-content-sdk/nextjs`.
When the General Link field is empty or has no `href`, the component renders nothing
for the CTA — no empty anchor, no placeholder button, no empty wrapper.

The CTA is styled as a button-like element: light/white background with dark text
(or a bordered/outlined style) to contrast against the dark scrim. Tailwind utility
classes provide the button styling. Hover and focus states follow the design system's
interaction model. The focus ring must be visible against the dark scrim — a light or
white focus ring or high-contrast outline is required.

### Responsive Behaviour

- **Mobile (below `lg`)**: Heading scales down (Tailwind responsive text classes, e.g.
  `text-3xl lg:text-5xl`). Subheading remains at body size. CTA maintains a minimum
  44×44px touch target. Horizontal padding from the design system spacing scale
  prevents text overflow. Text wraps naturally.
- **Desktop (`lg` and above)**: Heading at full H1 scale. Text content region
  constrained by a max-width to prevent excessively long lines on wide viewports.
- **All breakpoints**: Full-width, `60vh` height, centred content, layered structure
  (image → scrim → text) is consistent. No horizontal scrolling.

### Test Framework

Jest and React Testing Library are already installed and configured (`jest.config.js`,
`jest.setup.ts` exist; test infrastructure established by T001). No test framework
setup is needed for this task.

## Risks

### R1 — Full-Width Breakout and Parent Overflow

The full-width breakout technique (`-ml-[50vw] w-screen`) depends on the parent
container (`<div id="content">` inside `<main>`) not having `overflow: hidden` or
`overflow: auto` set. If the parent clips overflow, the hero will be cropped rather
than breaking out to full viewport width.

**Mitigation:** The Build agent should verify that no `overflow` constraint exists on
`<div id="content">` or `<main>` in `Layout.tsx`. If found, raise it to the
orchestrator. The current Layout.tsx does not apply overflow constraints to these
elements (confirmed by inspection).

### R2 — Sitecore Image Field Rendering as Background

The Sitecore SDK `Image` component renders an `<img>` element, not a CSS
`background-image`. Using absolute positioning with `object-fit: cover` to make the
`<img>` behave as a background works reliably in modern browsers, but the rendered
markup includes an `<img>` element rather than a container `div` with
`background-image`. This is the preferred approach for preserving SDK field editing
and alt text, but may require the Build agent to verify rendering under Experience
Editor mode.

**Mitigation:** If the Experience Editor interaction with the absolutely positioned
image is problematic, the Build agent should flag it but not switch to
`background-image` — maintaining alt text and SDK integration is the priority.

### R3 — Overlay Opacity Field Data Shape

The OverlayOpacity field is a Droplink referencing option items. The exact shape of
the field value in layout data depends on how Sitecore serialises the selected
Droplink item. It may arrive as a simple string value, a nested object with a `value`
property, or a reference with `fields`. The Build agent must inspect the actual layout
data shape when wiring the component and adapt the parsing logic accordingly.

**Mitigation:** The types file defines `OverlayOpacity` as `Field<string>` (the
simplest expected shape). If the runtime shape differs, the Build agent should update
the type definition and parsing logic to match. If the Droplink value structure cannot
be resolved without CMS access, a sensible fallback (default to 40%) should be used
until CMS integration is validated.

### R4 — Component Map Pollution

`sitecore-tools:generate-map` will register `heroBannerTypes` as a component entry.
This is a harmless dead entry that does not correspond to any Sitecore rendering
definition and will not cause runtime errors.

**Mitigation:** No action needed. This is consistent with the existing behaviour for
`headerTypes`, `footerTypes`, and other supporting files.

### R5 — Scrollbar Width and `100vw`

The `w-screen` / `100vw` approach can cause a slight horizontal overflow on systems
where the scrollbar occupies layout width (primarily Windows/Linux with classic
scrollbars). On macOS with overlay scrollbars, this is not an issue. The design note
states the hero must not cause horizontal scrolling at any viewport width.

**Mitigation:** The Build agent should verify that no horizontal scrollbar appears. If
it does, the breakout technique can be adjusted using `width: 100dvw` (dynamic viewport
width) or a `calc(100vw - var(--scrollbar-width))` approach. For the initial
implementation, `100vw` is acceptable as the primary target environment uses overlay
scrollbars.
