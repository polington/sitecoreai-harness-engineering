## Technical Approach

The Teaser Component is a single Sitecore rendering registered under `src/components/Teaser/` in the headapp at `src/headapps/rob-harness-engineering/`. It follows the established component pattern used by `HeroBanner` and `PromoCardGrid`: a PascalCase main component file, a camelCase types file, camelCase sub-component files, and a `__tests__/` folder — no barrel `index.ts`.

The component map scan path is `src/components` with exclusions for `content-sdk/*` and `**/__tests__/*`. The types file (`teaserTypes.ts`) and sub-components (`teaserImage.tsx`, `teaserActions.tsx`) use camelCase prefixes to avoid unintended component map registration under their base names.

The main `Teaser.tsx` is a server component. It reads all Sitecore-authored fields, resolves content sourcing (title/description/image from linked content item when sourcing flags are enabled), determines which variant is active, and renders the appropriate layout using Tailwind utilities. Variant layout logic is implemented as a lookup of variant-specific Tailwind class strings rather than a separate component per variant — this avoids duplicating the field-rendering logic across seven files.

The action area pattern addresses the nested navigation constraint directly: if a primary link is configured and no CTAs are present, the primary link wraps the image and content region. If CTAs are present, the primary link is not used as a wrapper; it is either omitted or rendered as a standalone link above the CTA list, depending on the authored value.

All sub-components (`teaserImage.tsx`, `teaserActions.tsx`) are server components that receive resolved field values; they do not access CMS data directly.

The Sitecore `Image`, `Link`, and `RichText` primitives from `@sitecore-content-sdk/nextjs` are used throughout, consistent with the project's existing delivery pipeline. No new SDK clients or alternate fetch paths are introduced.

The `headless-main` placeholder is already defined in the layout; the Teaser must be registered in the placeholder settings to be available for author placement (CMS prerequisite, not a code change).

### Slice 3 — Content sourcing resolution

**Purpose:**  
Implement the three content-sourcing rules: title, description, and image can each be resolved from a linked content item when the corresponding sourcing flag is enabled. Directly authored values take precedence when sourcing is disabled.

**Likely areas affected:**
- `src/headapps/rob-harness-engineering/src/components/Teaser/Teaser.tsx` (update)
- `src/headapps/rob-harness-engineering/src/components/Teaser/teaserTypes.ts` (update — linked-item field types)

**Implementation notes:**
- The sourcing flags (`TitleSourcing`, `DescriptionSourcing`, `ImageSourcing`) are Sitecore checkbox fields that resolve to a boolean.
- The linked content item is a general link or item reference field. When sourcing is enabled and the linked item exists, the appropriate field is read from the linked item's fields. When sourcing is enabled but no linked item is configured, fall back to treating the field as if no content is present (omit the region).
- Sourcing resolution should be implemented as a small set of pure helper functions inside `Teaser.tsx` (not a separate file) to keep the logic co-located and testable.
- The component must not render stale directly authored content when sourcing is enabled — the check is: `if (sourcingEnabled && linkedItem?.fields?.Title?.value) use that; else use direct field`.

**Validation focus:**  
Title sourcing enabled → title from linked item. Description sourcing enabled → description from linked item. Image sourcing enabled → image from linked item (or current item if no link). Sourcing disabled → directly authored value used. No sourcing path silently substitutes wrong content.

### Slice 4 — Action area and primary link model

**Purpose:**  
Implement the `teaserActions.tsx` sub-component for CTA links and integrate the primary link wrapping model. This slice handles the nested navigation constraint: primary link and CTAs must coexist without creating ambiguous nested interactive elements.

**Likely areas affected:**
- `src/headapps/rob-harness-engineering/src/components/Teaser/teaserActions.tsx` (new)
- `src/headapps/rob-harness-engineering/src/components/Teaser/Teaser.tsx` (update)

**Implementation notes:**
- **No CTAs, primary link present**: wrap the image and content region (but not any action element) in the SDK `Link` component using the primary link field. The accessible name is derived from the title value.
- **CTAs present, primary link present**: do not use primary link as a wrapper. Render each CTA as an independent SDK `Link` element in the action area. The primary link value may be exposed as an additional standalone link if it carries distinct labeling, or omitted at the component level (deferred to authoring guidance).
- **CTAs present, no primary link**: render each CTA independently.
- Each CTA action item is a child item in the multilist field, providing a `Label` (text) and `Link` (destination) field.
- The `teaserActions.tsx` sub-component receives the resolved list of action items and renders them with the design system's filled uppercase CTA treatment.

**Validation focus:**  
Primary link wraps content when no CTAs present. Primary link does not wrap CTAs when CTAs are present. Each CTA renders with its own label and href. Keyboard focus reaches each CTA independently. Primary link accessible name matches the teaser title.

### Slice 5 — Variant layout system

**Purpose:**  
Implement variant-driven Tailwind layout for all seven presentation variants: `default`, `featured`, `hero`, `card`, `list`, `slide`, and `secure`. Each variant applies a distinct set of layout, spacing, typography, and image-treatment classes while the content anatomy remains identical.

**Likely areas affected:**
- `src/headapps/rob-harness-engineering/src/components/Teaser/Teaser.tsx` (update)
- `src/headapps/rob-harness-engineering/src/components/Teaser/teaserImage.tsx` (update — variant-specific image height/crop classes)

**Implementation notes:**
- Variant is resolved from the `Variant` field value (string). A lookup object maps each variant name to its container, image region, and content region Tailwind class strings.
- Variants with overlay content (`hero`, `slide`) use CSS positioning. The image uses `object-cover` fill within a relatively positioned container; content uses absolute positioning on desktop, reverting to normal flow on mobile via responsive Tailwind prefixes.
- `featured` uses a `flex-row` split on `md:` and above; collapses to `flex-col` on mobile. Image region is `md:w-2/3`; content pane is `md:w-1/3` with a light-gray background.
- `card` uses a fixed-height image container (`aspect-square` or explicit height) with `overflow-hidden`. Pretitle renders as an absolutely positioned badge (`top-right`). Description is hidden. Hover class on the image (`group-hover:scale-105`) is supplementary only.
- `list` uses a compact horizontal layout: small image (`w-24` or similar) beside a text column; compact uppercase sans-serif title.
- `secure` variant applies a muted overlay to the image (`opacity-60` or similar) and a subdued action treatment. The restriction cue is rendered as part of this slice or Slice 6.
- Image focal positioning (`imagetop` / `imagebottom`) maps to `object-top` / `object-bottom` on the `<img>` element rendered by the SDK Image primitive.
- Unknown or missing variant values fall back to `default`.

**Validation focus:**  
All seven variants render at expected breakpoints without horizontal overflow. Featured split collapses correctly on mobile. Hero and slide overlay content moves to document flow on mobile. Card image clips cleanly. Hover effects are supplementary and do not hide destinations. Image focal positioning classes are applied correctly.

**Likely areas affected:**
- `src/headapps/rob-harness-engineering/src/components/Teaser/Teaser.tsx` (update)

**Implementation notes:**
- The restriction cue is rendered as a visually positioned element near the upper-left of the secure teaser, containing both an icon (SVG or equivalent) and a visible text label (e.g., "Members only" or an authored restriction label field if one is provided).
- The icon is decorative (`aria-hidden="true"`); the visible text carries the accessible meaning.

- The `secure` variant's CTA uses a subdued Tailwind treatment (lower opacity or neutral color) compared to the default filled CTA.

**Validation focus:**  
Restriction cue renders in secure variant. Cue contains visible text, not only icon. Icon is excluded from accessibility tree. Teaser remains interactive (links and CTAs are not disabled). Muted image overlay is visible. Non-secure variants do not render the restriction cue.

## Risks

**Nested navigation in overlay variants**: the `hero` and `slide` variants position content over an image. Wrapping the entire content region in a primary link while using CSS `position: absolute` for the content panel may require careful z-index and focus-order management to avoid invisible focus rings or focus being trapped behind the image layer. The implementation should verify that the focus ring for the primary link is visible above the image in all overlay variants.

**Content sourcing with partial linked items**: the linked item field may resolve to an item that has some but not all of the sourced fields. The implementation must handle each sourced field independently — title sourcing can succeed while image sourcing falls back — without treating the linked item as all-or-nothing.

**Component map registration pollution**: adding four new files to `src/components/Teaser/` increases the risk of an accidental component map entry if a file is named with a PascalCase base name. All supporting files must use camelCase prefixes (`teaserTypes`, `teaserImage`, `teaserActions`). The regenerated map files should be inspected after `generate-map` runs to confirm only `Teaser` is added.

**CTA actions multilist pattern**: the existing `PromoCardGrid` uses a flat `Cards` field with a card type. The Teaser `Actions` field is a multilist pointing to action items, each with their own `Label` and `Link`. This may require a different field-reading approach (iterating a list of child item fields rather than a flat array). The correct SDK pattern for multilist field resolution should be confirmed from existing usage or SDK documentation before implementation.

**Secure variant default restriction label**: the restriction cue requires a visible text label. If no restriction label field is authored on the Teaser data source template, a hardcoded default string (e.g., "Members only") is required. The hardcoded string should be confirmed with content/design before implementation to avoid shipping placeholder copy.

## Assumptions

- The existing `headless-main` placeholder is defined in `src/Layout.tsx` or the corresponding layout/page file and does not need to be created; only the CMS placeholder setting entry needs to be updated.
- The SDK `RichText` primitive from `@sitecore-content-sdk/nextjs` handles sanitization and structural preservation for the description field. The component does not need a separate sanitization library.
- The actions multilist field on the Teaser data source template returns an array of child items accessible via `fields.Actions` in the component props, following the same pattern as `fields.Cards` in `PromoCardGrid`.
- The linked-content-item sourcing field resolves as a General Link or Droptree reference. The resolved linked item's fields are accessible via a nested `fields` property on the link value — this pattern may require verification against the SDK's linked-item resolution behavior.
- Heading levels H2, H3, and H4 cover the allowed design-system range for this component. H1 is excluded (reserved for the page-level title). H5 and H6 are excluded as outside the design system's documented heading scale.
- The carousel container for the `slide` variant is not part of this task. The slide variant implements only the teaser's internal layout. No carousel integration contract is imposed on the Teaser component at this stage.
- The `secure` variant does not need a restriction label field in this implementation. A hardcoded default text string is acceptable for the first delivery, pending content team confirmation.
