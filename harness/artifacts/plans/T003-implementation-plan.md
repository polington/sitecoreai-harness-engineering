## Technical Approach

Create a single GitHub Actions workflow file at `.github/workflows/ci.yml` that triggers on pull request events targeting the default branch. The workflow contains one job with sequential steps: checkout, Node.js setup with npm caching, dependency installation via `npm ci`, followed by three validation steps (test, lint, type-check).

All npm commands use the `working-directory` option set to `src/headapps/rob-harness-engineering/` to scope execution to the head application.

The `actions/setup-node` action's built-in `cache: 'npm'` option handles dependency caching, using `package-lock.json` as the cache key.

Node.js 22 (current LTS) is the target runtime, consistent with the project's dependency requirements (Next.js 16, TypeScript 5.8).

No additional npm scripts need to be created. The existing scripts cover testing (`npm test`) and linting (`npm run lint`). Type-checking uses `npx tsc --noEmit` directly since no dedicated script exists.

Branch protection documentation will be added as a section in the workflow file's header comments, providing clear instructions without requiring a separate documentation file.

## Implementation Steps

### Step 1 — Create the workflow directory and file

Create `.github/workflows/ci.yml` with:

1. A top-level `name` field (e.g., `CI`).
2. Branch protection documentation as YAML comments at the top of the file.
3. Trigger configuration: `on.pull_request` with types `[opened, synchronize, reopened]` and branches targeting the default branch.

### Step 2 — Define the job

Add a single job (e.g., `validate`) running on `ubuntu-latest`.

### Step 3 — Add checkout step

Use `actions/checkout@v4` to check out the repository.

### Step 4 — Add Node.js setup step

Use `actions/setup-node@v4` with:
- `node-version: '22'`
- `cache: 'npm'`
- `cache-dependency-path: 'src/headapps/rob-harness-engineering/package-lock.json'`

The `cache-dependency-path` is required because `package-lock.json` is not in the repository root.

### Step 5 — Add dependency installation step

Run `npm ci` with `working-directory: src/headapps/rob-harness-engineering`.

### Step 6 — Add test step

Run `npm test` with `working-directory: src/headapps/rob-harness-engineering`.

### Step 7 — Add lint step

Run `npm run lint` with `working-directory: src/headapps/rob-harness-engineering`.

### Step 8 — Add type-check step

Run `npx tsc --noEmit` with `working-directory: src/headapps/rob-harness-engineering`.

## Risks

- If the `lint` script's glob pattern (`./src/**/*.tsx ./src/**/*.ts`) does not match any files in CI (e.g., due to shell globbing differences between local and CI environments), ESLint may exit silently or error. The workflow should not suppress exit codes.
- The `npm ci` command requires an exact match between `package.json` and `package-lock.json`. If they are out of sync, the CI job will fail — this is expected and desirable behavior.
- GitHub-hosted runners may have different system-level dependencies than local development environments. The head application's tests should not depend on system-level state, but this should be monitored after the first CI run.
